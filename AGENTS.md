# create-faster

CLI that scaffolds projects from Handlebars templates. Interactive prompts or flags pick one or more apps (Next.js, Expo, Hono, Node, TanStack Start), libraries per app, and project-level choices (database, ORM, deployment, linter, tooling). Two or more apps produce a Turborepo, one app a single repo. Blueprints are pre-composed projects with application code.

Install and run: `bunx create-faster`. License: MIT. The published package is `apps/cli`.

## Repository layout

```
apps/cli/                  # The CLI (TypeScript, Bun)
  src/                     # Source, imported through the `@/*` alias
  templates/               # Handlebars templates (see Template system)
  tests/                   # unit, integration, e2e, blueprints
apps/www/                  # Documentation site (Next.js + Fumadocs), content in apps/www/content/docs
packages/config/           # Shared tsconfig
docs/agents/               # Research, plans and audits written by agents
.claude/skills/            # Repo skills for Claude Code (see Skills)
```

| `lib/frontmatter.ts`, `lib/file-writer.ts` | Frontmatter parsing, stack suffixes, special filenames, directory scan |
| `lib/package-json-generator.ts` | Programmatic `package.json` generation from META |
| `lib/env-generator.ts` | Programmatic `.env.example` generation from META |
| `lib/agent-context-generator.ts` | `AGENTS.md` and `CLAUDE.md` of generated projects |
| `lib/addon-utils.ts` | Compatibility and requirement checks, script placeholders |
| `lib/script-list.ts` | The Scripts list of the READMEs and `AGENTS.md`: the root scripts with the sentences META declares for them (`scriptDescriptions`, `productionScripts`) |
| `lib/syncpack-config.ts` | The `syncpack` config of a turborepo root, generated from META (`collectSyncpackConfig`): the workspace packages and the `pinnedPackages` of each app are left out of the version comparison |

## Commands

Run from the repository root unless noted. Bun is the package manager (`packageManager` in `package.json`; `apps/cli` requires `bun >= 1.3.1`).

```bash
bun install                  # Setup (also installs the husky hooks)
bun run dev:cli              # Run the CLI from source
bun run build:cli            # Build apps/cli to dist/
bun run check                # Biome format + lint check (CI runs it)
bun run lint                 # Biome lint with auto-fix
bun run format               # Biome format
bun run check:unused         # knip (CI runs it; config in knip.jsonc)
bun run typecheck            # tsc --noEmit on apps/cli and apps/www (CI runs it); apps/www first runs next typegen, then fumadocs-mdx (keep that order: next typegen exits while the fumadocs-mdx Next plugin is still writing .source/index.ts, which leaves it empty)
cd apps/cli && bun test tests/unit tests/integration
cd apps/cli && bun test tests/e2e/<file> --timeout 600000
```

- `tests/unit` and `tests/integration` run in CI. Integration tests run the real CLI and assert on generated files (`tests/integration/helpers.ts`).
- Integration tests get a longer per-test timeout than unit and e2e tests, whichever command runs them: `tests/integration/timeout.ts` exports `setIntegrationTimeout()`, which calls `setDefaultTimeout` from `bun:test`, and every `tests/integration/*.test.ts` imports it from `./timeout` and calls it at the top level, after its imports (`setIntegrationTimeout();`). The call has to be in each file: Bun evaluates a module once per run and the default timeout set in one file does not reach the next ones, so a bare `import './timeout';`, a shared helper or a `bunfig.toml` `preload` gives it to the first file of a multi-file run only (Bun issues oven-sh/bun#43787 and #45192; `bunfig.toml` has no test timeout option either). A `--timeout` flag on the command would also hit the unit tests of `bun test tests/unit tests/integration`, and a single file run without it. The call also reaches hooks (`beforeAll`), and unit tests keep Bun's 5 s and e2e its `--timeout`, because only the files that call it get the default; keep it out of shared helpers, which e2e and unit tests import too. Many integration tests run the real CLI several times and exceed 5 s on a loaded machine (another build, a dev server). `tests/unit/integration-timeout.test.ts` fails, naming the file, when an integration test forgets the import or the call, and runs three files under `bun test --timeout 100` to check that the hooks and tests of each one outlast it.
- `tests/e2e` generates, installs and builds real projects. It is slow, needs network, and runs on demand, one file at a time.
- Biome does not lint `apps/cli/tests`.
- Tests read plain CLI output whatever the terminal or CI asks for: `apps/cli/bunfig.toml` preloads `tests/setup.ts` (in-process output) and `runCli` passes the same variables to the child CLI (`tests/plain-output-env.ts`: `NO_COLOR=1` and `FORCE_COLOR=0`, because picocolors lets `NO_COLOR` win over `FORCE_COLOR` and `CI` while Bun's own console lets `FORCE_COLOR` win). Never strip escape codes inside a test. A test that needs colors passes `{ NO_COLOR: '', FORCE_COLOR: '1' }` to `runCli`.

## Declarative choice logic (mandatory)

**Every agent MUST follow this. No exception without explicit approval from the maintainer.**

NEVER hardcode logic tied to a specific choice value (a stack, library, deployment, database, ORM, linter, blueprint, etc.) inside core logic: the resolver, the file generator, the flags parser, the prompts engine, or any shared algorithm. Core code stays agnostic to which choices exist.

Forbidden:
- A literal branch on a choice value in core logic: `if (deployment === 'cloudflare-static')`, `if (stack === 'nextjs')`, `if (library === 'better-auth')`.
- An incompatibility, compatibility or support list hardcoded in a `.ts` core file (for example `const CLOUDFLARE_STATIC_INCOMPATIBLE_LIBRARIES = [...]`). That data belongs in META, read generically.
- Choice-specific output paths, filtering or skipping written as special cases in the resolver.

Required: choice-specific behavior is expressed through reusable operators that core logic applies generically.

- **Handlebars helpers** (`apps/cli/src/lib/handlebars.ts` is the list):
  - `eq`, `ne`, `and`, `or`: `and` and `or` read an empty list as false, as `{{#if}}` does, so `(or (appSecrets) ...)` works
  - `isMono`: the project is a turborepo
  - `hasLibrary(name)`: the current app has the library; outside an app-scoped file, any app has it
  - `has(category, value)`: `database`, `orm`, `deployment`, `linter` or `tooling` selection; `has "stack" "x"` is true when any app uses the stack
  - `databaseBinding(name)`: true when the selected database declares `serverlessBinding: name` in META (`{{#if (databaseBinding "hyperdrive")}}`), so a new binding database needs no template edit
  - `hasContext(key)`: the key exists in the context
  - `hasPackage(name)`: a turborepo workspace package of that name is generated (it gets a `package.json`), from `collectMonoPackages` in `package-json-generator.ts`; false in a single repo. Use it to describe `packages/db` (`{{#if (hasPackage "db")}}`), never `project.orm`; it also works inside `{{#each}}` blocks
  - `monoPackages`: the names of the workspace packages a turborepo generates (the keys `collectMonoPackages` returns), for `{{#each (monoPackages)}}`; empty in a single repo. Inside that block `this` is the name, so `hasLibrary` (which reads the context) does not work there: put it outside the block. `has` reads the project, so it works in any block
  - `appSecrets`: the names of the secret variables the current app receives (`EnvVar.secret`, same per-app rules as `env-generator`: library envs only for apps with the library, `stacks` and `when` honored, never a `file` variable), from `collectAppSecrets` in `env-generator.ts`; empty outside an app-scoped file. The `cloudflare/secrets-required` partial renders them as `secrets.required` in every `wrangler.jsonc`
  - `projectSecrets(stack, ...)`: the names of the secret variables received by at least one app on one of the listed stacks, each once (`collectProjectSecrets` in `env-generator.ts`), for `{{#each (projectSecrets "nextjs" "hono")}}`. The `sst` deployment declares one `sst.Secret` per name from it, so a secret no deployed app reads (an app on a stack SST does not deploy) is never required
  - `receivesEnv(name)`: the current app's `.env` receives the variable `name` (`collectAppReceivesEnv` in `env-generator.ts`: a selected choice declares it, it reaches this app through its libraries, `stacks` and blueprint app, and it is not a dedicated-file variable); false outside an app-scoped file. A file or block that only means something when the app declares a variable gates itself on it, so the template reads exactly what META declares (`src/lib/get-app-url.ts` and the portless `env` of `next.config.ts`, gated on `NEXT_PUBLIC_APP_URL`)
  - `hasAppScript(name)`: some app's generated `package.json` defines the script (`getAppScripts` in `package-json-generator.ts`), whether or not a turborepo root forwards it; `hasRootScript` answers for the root. Use it for a note about a script only the apps define (`preview`).
  - `appOriginEnvs(stack, ...)`: the `.env` of each app and its variables that are the origin the app is served from (`EnvVar.origin`), `{ path, names }[]` (`collectAppOriginEnvs` in `env-generator.ts`, same per-app selection as `appSecrets` through `collectAppEnvNames`, never a package or `file` variable), narrowed to the apps on the listed stacks when any are given, for `{{#each (appOriginEnvs)}}`; empty when no app has one. The `env/app-url-variables` partial renders one entry as a line (`` - `apps/web/.env`: `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL` ``)
  - `envFiles`: the names of the dedicated env files (`EnvVar.file`) the project receives (`collectEnvFileNames`), for `{{#each (envFiles)}}.env.{{this}}{{/each}}`; both `.gitignore` templates list them, so a new `file` variable is ignored with no template edit
  - `taskEnv(task)`: the names of the variables whose META `EnvVar` lists the Turborepo task in `tasks` (`collectTaskEnv` in `env-generator.ts`), for `{{#with (taskEnv "db:seed")}}`; see `envs` `tasks` in META capabilities
  - `appUrl(name)`: the dev URL of the app (`http://localhost:{port}`, or the URL a selected tooling addon provides, as for the `{{appUrl}}` env placeholder), or an empty string when the app does not serve on a port (none of its scripts carries the `{{port}}` placeholder: Node, Expo)
  - `hasRootScript(name)`: the generated root `package.json` (the turborepo root, or the single app's) defines the script, derived from META by `getRootScripts` in `package-json-generator.ts`; renders a CI step only when the script exists. A turborepo root gets `turbo build`, `turbo dev`, `turbo start`, `turbo test`, `turbo test:e2e` and `turbo cf-typegen` (`APP_SCRIPTS_RUN_BY_TURBO`) when at least one app declares the script, and `turbo.json.hbs` declares the matching task under the same `hasRootScript` condition (`dev` too: a turborepo of Expo apps only has no root `dev`, no `dev` task, and its README and fiche print no `dev` step; the same holds for `build`: Expo apps and Hono or Node apps on npm or pnpm declare none, so a turborepo of them has no root `build`, no `build` task and no printed build step, and the `test` task drops its `^build` dependency, which Turborepo rejects as a missing task when no `build` task exists; the `github-actions/lint-and-build` partial renders its Build step under the same condition)
  - `installScripts`: the install-script policy of the selected choices, `{ <package>: boolean }` (`collectInstallScripts` in `lib/install-scripts.ts`), for `{{#each (installScripts)}}` with `@key` and `this`; nothing (falsy) when no selected choice brings a dependency with an install script. The `pnpm/allow-builds` partial renders it as `allowBuilds`
  - `firstRunSteps`: the first-run steps of the project (`{ description, commands }[]`, commands already resolved for the package manager), for `{{#each (firstRunSteps)}}`; see First-run steps
  - `manualPostGenerateSteps`: the `postGenerate` steps the user runs themselves (`{ description, commands }[]`, the shape of `firstRunSteps`), `collectManualPostGenerateSteps` in `lib/post-generate.ts`: all of them when the CLI does not install (`--no-install`, or no package manager selected: `installsDependencies`), none when it installs and runs them itself. The `readme/post-install` partial renders them right after the install command in both Getting Started sections, as the summary does, so a `--no-install` README tells to run `npm run format` like the next steps; it and `readme/first-run` render each step through the one `readme/command-step` partial (the caller adds the blank line after it)
  - `blueprintSeed`: the `seed` of the selected blueprint (`getBlueprintSeed` in `addon-utils.ts`), `{ rows, deletes, target? }`, or nothing (falsy) when the blueprint declares none or there is no blueprint; `{{#if (blueprintSeed)}}` chooses between the `seed/blueprint` partial and the ORM seed sentence `seed/deletes-users`; see the blueprint seed in META capabilities
  - `generatedFiles(tool)`: the patterns one tool (`biome`, `eslint`, `oxfmt`, `oxlint` or `prettier`) must ignore, for `{{#each (generatedFiles "biome")}}`: the committed files that the tools of the selected choices write, from the `generatedFiles` of the selected project addons, libraries, stacks and blueprint (`collectGeneratedFiles` in `lib/generated-files.ts`, in that order, each pattern once). The ignore lists of `biome.json`, `packages/eslint-config/next.js` and the single-repo ESLint config, `oxlint.config.mts`, `oxfmt.config.mts` and `.prettierignore` render it, so a linter or formatter never rewrites a file that has to stay byte-identical to the output of its tool, and a choice with such files is a META field, never a template edit. See `generatedFiles` in META capabilities.
  - `hasAppFile(path)`: the project generates a file at that path in an app (`src/middleware.ts`), in a single repo or under `apps/<app>/` in a turborepo (the destinations `getAllTemplatesForContext` resolves, once per project). A note that describes a file only means something when the file exists, so it gates itself on this, never on the choice that decides the file (`cloudflare/opennext-warnings` and the request hook `src/middleware.ts`, which a blueprint with no hook does not have).
  - `hasBlueprintPartial(name)`: the selected blueprint, or a blueprint it `extends`, has the partial `partials/blueprints/<blueprint>/<name>.hbs`. Use it where a shared template lets a blueprint replace a block (the deploy step of `cloudflare/d1-provisioning`) instead of adding to it, which `blueprintPartial` does.
  - `appSecretDetails`: the secrets of the current app as `{ name, command?, origin }[]` (`collectAppSecretDetails` in `env-generator.ts`, the selection of `appSecrets`): `command` is the `generateCommand` of the variable and `origin` says its value is the public URL of the app. The `cloudflare/first-deploy` partial reads it to generate each secret in the shell and to write the secrets file.
  - `deploySecrets`: the secrets a deploy needs a value for in the shell, `{ name, command? }[]` (`collectDeploySecrets` in `env-generator.ts`): those of every app, each once, an `origin` secret left out (the exported production URL gives it). It gates and fills the secrets step of `cloudflare/first-deploy` with no list of stacks, so an app on any stack is covered; the step is absent when it is empty.
  - `seedFile`: where the seed script of the selected blueprint lives (`file` of its `seed`, `scripts/seed.ts` when it declares none), for the sentence of `seed/blueprint`.
  - `thirdPartyEnvs`: the ids of the user's own third-party accounts the project receives, `{ name, description, url, whenBlank, paths }[]` (`collectThirdPartyEnvs` in `env-generator.ts`: the variables whose META `EnvVar` declares `thirdParty`, with the per-app selection of the `.env.example` files and the `.env` of each app that reads them, never a package or a `file` variable), for `{{#each (thirdPartyEnvs)}}`; empty when the project has none. The `env/third-party-ids` partial and the `setup/missing-config` partial read it; see Third-party ids
  - `productionSteps`: the commands that build, serve or ship the project (`{ description, command }[]`, `collectProductionSteps` in `lib/production-steps.ts`), for `{{#each (productionSteps)}}`; empty when the project has none. The scripts and their sentences are META data, `productionScripts` on the stacks of the apps and on the selected project addons (see META capabilities), so a new deployment or stack adds its own with no edit to core code. A declared script is printed only when the project defines it: a project without a `build` script prints no build step, and a deployment's own `build:cf`, `preview` and `deploy` appear with no branch on the deployment. A script the generated root `package.json` defines (`getRootScripts`, as `hasRootScript`) prints as a root command; a script only the apps define (`getAppScripts` in `package-json-generator.ts`: the scripts of each app, which in a turborepo the root does not forward) prints one line per app that has it, as a subshell that leaves the shell at the root (`(cd apps/web && npm run deploy)`, valid under bun, npm and pnpm; `getScriptCommandInApp`), so the steps paste in order. The order is per app, because the stacks declare their scripts in different orders (Start's `preview` precedes the deployment's `build:cf` that a Next.js app needs first): root commands come first, in the order the stacks of the apps and then the addons declare them; then each app in turn gets its own app-only steps, in that app's own declared order (its stack, then the addons), so an app's `build:cf` precedes its `preview` and `deploy` whatever the other apps declare. Both READMEs, both `AGENTS.md` fiches (Scripts), the `cloudflare-static-site-nextjs` README and `buildStepsNote` in `tui/summary.ts` all read it, so they cannot drift. The `dev` step is printed only when the root defines `dev` (`hasRootScript "dev"` in the `readme/getting-started` partial and the single-repo fiche, `getRootScripts` in the summary).
  - `scriptList`: the root scripts of the generated project with their sentences (`{ command, description, readmeSection? }[]`, `collectScriptList` in `lib/script-list.ts`), for `{{#each (scriptList)}}`; the `scripts/root-list` partial is that loop and holds no script name or sentence. The sentences are META data, `scriptDescriptions` and `productionScripts` (see META capabilities), so a new root script is described where it is declared. Which scripts appear is derived from the generated root `package.json` (`getRootScripts`), so a script only the apps define is not listed, and the scripts the package manager runs itself (`prepare`, `postinstall`, `predev` for `dev`: `isLifecycleScript`) never are
  - `scriptDescription(name)`: the sentence META declares for the script (`describeScript`), or an empty string; the `dev` sentence of both READMEs (`{{scriptDescription "dev"}}:`) and of the CLI summary comes from it
  - `interactiveSteps`: the commands to run an interactive script of an app from its directory (`{ description, command }[]`, `collectInteractiveSteps` in `lib/interactive-steps.ts`), for `{{#each (interactiveSteps)}}`; empty in a single repo and when no app of the project has one. They come from `interactiveScripts` of the stacks of the apps (see META capabilities), so a stack adds its own with no edit to core code; the `scriptList` helper (the Scripts list of both repo types) puts them after the scripts of the stacks, the turborepo README prints them as a command block after the `dev` one, and the summary lists them under Development (a sentence ending with the app name, `Run dev:expo in a terminal of its own (mobile)`, as every app-only step). The `dev` sentence says that the turborepo root `dev` runs "every app that has a `dev` script", and the README block and the `dev` list line exist only when the root defines `dev`. `interactiveScript` returns the interactive script the current app defines (empty in a single repo, where the app keeps `dev`): the `expo/dev-server` partial writes the dev command of the Expo fiches from it, so no template writes the script name.
  - `runScript(name)`: a package.json script as the selected package manager runs it (`bun run build`, `npm run build`, `pnpm run build`; `npm` when none is selected). An optional second argument forwards flags to the script, with the `--` npm needs (`{{runScript "db:seed" "--fixtures"}}` is `npm run db:seed -- --fixtures`, `bun run db:seed --fixtures`). Docs and notes written into generated projects never write `{{pm}} build`: a bare `bun build` is Bun's bundler and `npm build` is an unknown command
  - `tsRunner`: the command that runs a TypeScript file under the selected package manager (`bun`, or `tsx` for npm and pnpm; data in `package-manager.ts`). A script that runs a `.ts` file starts with it, and `tsx` is declared as a devDependency under `$when({ pm: { not: 'bun' } })`
  - `runAppScript(name)`: a script only the apps define (`deploy`, `preview`, `build:cf`: a turborepo root has none) as a user runs it: `runScript` in a single repo, `(cd apps/<app> && <runScript>)` in a turborepo (the subshell of `inDirectory`), valid under every package manager. A script the root forwards to every app through turbo (`dev`, `build`, `cf-typegen`) stays `runScript`
  - `listeningApps`: the apps that serve on a port (a script carries the `{{port}}` placeholder, the rule that gives `appUrl` a URL), for `{{#each (listeningApps)}}`; empty when no app listens (Expo, Node), so `{{#if (listeningApps)}}` gates a block that only means something for an app with a port. Inside the block `this` is the app, so `hasRootScript` and `hasLibrary` do not work there
  - `stackApps(stack)`: the apps on a stack, for `{{#each (stackApps "nextjs")}}`; inside the block `this` is the app, so `hasLibrary` does not work there (`has` does). `{{> cloudflare/app-list stack="nextjs"}}` renders their names, for the note that tells which apps a per-app command applies to
  - `packageRunner`: the selected package manager's binary runner (`bunx`, `npx`, `pnpm dlx`; `npx` when none is selected), data in `package-manager.ts`
  - `installedBinaryRunner`: the command that runs a binary a dependency of the project installed (`bunx`, `npx`, `pnpm exec`), in the version the project pins. `packageRunner` (`pnpm dlx`) downloads the latest release whatever the project pins, so it is only for a one-off package (`shadcn@latest`); the documented commands of the project's own `wrangler`, `drizzle-kit` and `sst` use `installedBinaryRunner`. Run it from a directory whose `package.json` declares the binary: a turborepo root declares none of `wrangler` and `drizzle-kit`, and under bun and pnpm only the package that depends on a binary links it
  - `joinEntries` and `entry`: block helpers for a list whose items depend on conditions and are separated by commas, as the tasks of `turbo.json.hbs`. `{{#joinEntries open="{" close="}" closeIndent="  "}}` contains one `{{#entry}}...{{/entry}}` per item (the condition goes inside the entry, so it is written once); an entry that renders only whitespace is dropped, the kept ones are joined with `,` and a line break, each keeping its own indentation, and the result is wrapped in `open`/`close` (the closing one indented by `closeIndent`), or is just `open` followed by `close` (`{}`) when no entry remains. Without `open` and `close` the joined entries are returned bare. An `entry` outside `joinEntries` throws. A `{{/joinEntries}}` alone on its line swallows the line break that follows it, so put it on the line of the last `{{/entry}}` when text must follow on its own line
  - `orderedSteps` and `step`: block helpers for a numbered list whose steps depend on conditions, as the D1 provisioning steps. `{{#orderedSteps}}` contains one `{{#step}}...{{/step}}` per step (the condition goes inside the step, so it is written once); a step that renders only whitespace is dropped, the kept ones are numbered `1.`, `2.`, ... on their first line, separated by a blank line, and the result ends with a line break (nothing when no step remains). A step's continuation lines (the code fence, the sub-list) carry their own three-space indentation. A `step` outside `orderedSteps` throws. Markdown auto-numbering is not used because the steps hold fenced blocks, and the numbers must be right in the raw text.
  - `deployAppDir`: the name of the app whose `wrangler.jsonc` the deployment scripts use (`resolveDeployAppDir`, the same app as the `{{deployAppDir}}` script placeholder: an app on a stack the deployment supports, preferring one with a `needsSingletonDb` library), empty without a deployment. Use it for a command that must run in that app (`wrangler d1 create`), never `apps.0`: the first app can be an Expo app
  - `inDirectory(...segments)`: a block helper, `{{#inDirectory "packages" "db"}}...{{/inDirectory}}`, that renders its content from that workspace directory as a subshell in a turborepo, `(cd packages/db && ...)`, and unchanged in a single repo, which keeps everything at its root. The subshell leaves the shell where it was, so printed steps paste in order. `getCommandInWorkspaceDirectory` is the one owner of that form (`getScriptCommandInApp`, behind `productionSteps`, and `getAppScriptCommand`, behind `runAppScript`, share it), so the README, `AGENTS.md` and the CLI summary print app commands alike; a template never writes `cd <dir> &&` for a command a user pastes
  - `blueprintPartial(name)`: the partial `partials/blueprints/<blueprint>/<name>.hbs` of the selected blueprint (or of the nearest blueprint it `extends`), for `{{> (blueprintPartial "first-admin")}}` in a template every project shares; an empty partial, so the line disappears, when the blueprint has none or there is no blueprint. A choice's own facts (a blueprint's app names, outputs, URLs, commands) live in that partial, never behind `{{#if (eq blueprint "x")}}` in the shared template. A partial block cannot do this (`{{#> (name)}}` has no closing tag in Handlebars), hence the helper
  - `camelCase`, `pascalCase` (`DATABASE_URL` and `web-app` become `DatabaseUrl` and `WebApp`), `raw`, `appPort(name)` (3000 + app index)
  - Express conditionals inside templates: `{{#if (has "deployment" "cloudflare")}}...{{/if}}`.
- **Handlebars partials** (`apps/cli/templates/partials/`, registered by `setupTemplateEngine` in `apps/cli/src/lib/handlebars.ts`): `{{> group/name}}` inserts a block that several templates share, rendered with the caller's context plus optional hash parameters. A choice mapping written in several templates (for example stack to better-auth cookie plugin) lives once in a partial, expressed with the helpers above. See Template system, Partials.
- **Frontmatter keys** (`TemplateFrontmatter` in `apps/cli/src/types/meta.ts`, applied generically in `template-resolver.ts`): `path`, `mono` (`scope`/`name`/`path`), `only` (`mono`, `single`, `no-blueprint`), `deploymentPath`, `deploymentSkip`, `blueprintSkip`. `only` and the deployment and blueprint skip keys are honored for every template kind (stack, library, project addon, stack-suffixed addon, repo, blueprint). They are the model: a generic key the resolver honors for ANY value.
- **META data** (`__meta__.ts`; types in `types/meta.ts`): `support`, `require`, `mono`, `packageJson`, `rootPackageJson`, `stackPackageJson`, `deploymentPackageJson`, `appPackageJson`, `envs`, `compose`, `runtime`, plus the capability flags below. Compatibility and dependency rules live here as data, validated generically.
  - `stackPackageJson`: per-app-stack dependencies. Honored for libraries, deployments and databases; for a database it lands in each matching app in single and turborepo alike. For example `sqlite` adds `@libsql/client` (same version constant as the db package) to TanStack Start apps running Nitro, so the app resolves it and Nitro externalizes it and traces `libsql` with its native binding instead of bundling it.
  - `packageManagerPackageJson`: `Partial<Record<pm, PackageJsonConfig>>` on a stack or a blueprint, merged by `package-json-generator` when the effective package manager (`npm` when none is selected) matches a key, for a script or dependency that differs between Bun and Node (`hono`: `tsx watch src/server.ts`, `@hono/node-server`). A `pm` key of `$when` covers a value inside a config; this covers a whole config.
  - `rootPackageJson`: `PackageJsonConfig` (values may be `$when`) for the keys only the repo root reads, such as npm `overrides`. On a library it is merged into the root `package.json` of a turborepo and into the app's `package.json` of a single repo, for every app that has the library on a supported stack (an app's own `package.json` in a turborepo never carries it); a blueprint's is merged the same way. A turborepo root takes them in `composeRootPackageJson`, a single repo's app `package.json` in `composeApp`. Keys other than dependencies, scripts and exports merge deeply (objects merge key by key, arrays and scalars are replaced), so a library and a blueprint contributing the same `overrides` entry both stay. `$when` conditions are resolved against the whole project, so `stack` and `library` keys follow any-app semantics: a library's root key applies to the whole root even when the `stack` it names is on another app. The `evlog` entry uses it to override its `nitro` peer under npm (the reasons are in a comment on that entry in `__meta__.ts`).
  - `deploymentPackageJson`: `Record<deployment, PackageJsonConfig>`, merged generically by `package-json-generator` when `ctx.project.deployment` matches a key. For example `postgres` adds `pg-cloudflare` under `cloudflare`.
  - `envs`: `EnvVar` with `value`, `monoScope`, an optional `when` (a `$when` match such as `{ orm: true }`: the variable is emitted only when it holds) and an optional `stacks: StackName[]`. When `stacks` is set the variable is emitted only for apps whose stack is listed, evaluated per app by `env-generator`, so one project can carry `NEXT_PUBLIC_X` on Next.js apps and `VITE_X` on TanStack Start apps. A root or pkg-scoped variable with `stacks` is emitted when at least one app (with the library, for library envs) has a listed stack. An optional `file` (a name such as `d1`) writes the variable to `.env.<file>.example` (same scope-to-path rules, in the generated project the file is `.env.<file>`) instead of `.env.example`. Use it for a secret that only a CLI reads, never a Worker or a framework: Wrangler, Vite and Next.js load `.env` (and `.env.local`, `.env.<mode>`) into the Worker environment, and OpenNext bundles it into the deployed Worker, while a `.env.<file>` of another name is read by nothing but the tool that loads it explicitly. A template that consumes such a file loads it itself (the drizzle `drizzle.config.ts` calls `process.loadEnvFile('.env.d1')`, the root `db:seed` of `cloudflare-fullstack-nextjs` passes `--env-file=.env.seed`), the generated `.gitignore` lists it through `envFiles`, the first-run env copy and `local-setup` create it from its `.env.<file>.example`, and OpenNext, which bundles `.env`, `.env.local` and their mode variants of the app and of the monorepo root, never sees it.
  - `envs` `tasks: string[]` names the Turborepo tasks that read the variable at run time (`DATABASE_URL` of a database and `SEED_PASSWORD` of a seeding blueprint list `db:seed`). `collectTaskEnv` keeps the variables the project receives (the same selection as the `.env.example` files: selected addons, libraries and blueprint, `when` and `stacks` honored), a `file` variable included when it names the task (the seed password of a Worker blueprint), each once; `turbo.json.hbs` renders them through `taskEnv` as the `env` of the task and omits the key when there is none, so Biome's `noUndeclaredEnvVars` and Turborepo's strict env mode see what the task reads. A new seed variable or database is a `tasks` entry, never a template edit.
  - `envs` `origin: true` marks a variable that is the origin the app is served from (`BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL`, both `{{appUrl}}`). It stays what the app was configured with when the port changes, so the port override notes list it (`appOriginEnvs`, see Changing the port of an app); a variable that only holds the URL (the `BASE_URL` of `playwright`) is not marked.
  - `envs` `secret: true` marks a variable the app reads at runtime from outside the repo and must be given in production (`BETTER_AUTH_SECRET`, `PRIVY_APP_SECRET`, and `BETTER_AUTH_URL`: better-auth rejects every host but `localhost` without it). Never a `NEXT_PUBLIC_*` or `VITE_*` value, which is baked into the client at build. A Cloudflare Worker lists the variables it receives in `wrangler.jsonc` under `"secrets": { "required": [...] }` (see Cloudflare). Wrangler keeps only the listed keys in the local `.dev.vars` of a Worker, so a runtime variable that is not marked is missing from `vite preview`; a variable that is a binding on Cloudflare (`DATABASE_URL` through Hyperdrive) stays unmarked. `secret` also takes a `$when` match (`secret: { deployment: 'sst' }`): the variable is a secret only where the match holds, so the `postgres` and `mysql` `DATABASE_URL` is a secret under `sst` and a binding under `cloudflare`. Under `sst`, `sst.config.ts` declares each runtime secret as an `sst.Secret` (named in PascalCase, `DatabaseUrl`, as SST requires) and gives it to the apps that read it through `environment: { DATABASE_URL: secrets.DatabaseUrl.value }`, so the app code keeps reading `process.env`. `link` is not used: a linked `sst.Secret` reaches the code only through `Resource.X.value` of the `sst` SDK, never as an environment variable. A deploy and `sst dev` fail until each one is set (`sst secret set DatabaseUrl <value> --stage <stage>`, or `SST_SECRET_DatabaseUrl` in CI); the generated `AGENTS.md` lists the commands (`project/deployment/sst/__agent.md.hbs`).
  - `envs` `generateCommand: string` is a command that prints a value for the variable (`BETTER_AUTH_SECRET`: `openssl rand -base64 32`), for a variable the production build or server cannot run with blank. The committed value stays blank, and `env-generator` appends `# generate with: <command>` to its `.env.example` line, so the comment is derived. `collectEnvsToGenerate` lists each such variable the project receives with the `.env` of every app that reads it (the filter of `collectAppSecrets`: the app scope, the root `.env` of a single repo, never a package or a `file` variable), and `collectFirstRunSteps` turns each into a step after the env copy that a blueprint's own `firstRun` does not replace. With several apps the step says to set one value in every file, as they share one auth database and sessions. One name carries one command in all of META (unit test).
  - `envs` `thirdParty: { description, url, whenBlank }` marks a variable that is an id of the user's own account on a third-party service (the PostHog project token, the Privy app ID, client ID and secret, the WalletConnect project ID): `description` names it (`Privy app ID`), `url` is where to get it, `whenBlank` says what the app does while it is blank (a sentence that follows "While it is blank, "). The committed value stays blank (a unit test fails on any other value), and `env-generator` appends `# <description>: <url>` to its `.env.example` line, so the comment is derived, as `# generate with:` is. `collectThirdPartyEnvs` lists each such variable the project receives with the `.env` of every app that reads it (the filter of `collectEnvsToGenerate`). The `thirdPartyEnvs` helper hands the list to the `env/third-party-ids` partial. One name carries one source in all of META (unit test). A value shared by several variables is a constant (`POSTHOG_TOKEN_SOURCE`, `PRIVY_DASHBOARD_URL`).
  - `postGenerate`: `PostGenerateStep[]` (`{ description, script }`) on a project addon, a package.json script the CLI runs once the dependencies are installed, through the selected package manager (`getScriptCommand`: `bun run format`, `npm run format`, `pnpm run format`). A raw shell string is not accepted: naming a script keeps it portable, and the script must exist on the generated root `package.json` in a single repo and in a turborepo (a unit test checks every declaration). `collectPostGenerateSteps` (`lib/post-generate.ts`) returns the steps of the selected addons in the order of the `META.project` categories, a composite addon (`compose`) contributing the steps of the addons it composes; `runPostGeneration` runs them after a successful install, so the first commit is formatted (the CLI makes no commit itself). The linters with a formatter declare the script that leaves their own check passing: `oxc` and `prettier` (and `eslint-prettier`, through `compose`) `format`, `biome` `check` (`biome format` does not sort imports, which `biome check` enforces); `eslint` has none. A failing step never fails the generation (the files are valid, only unformatted): it warns with the command to rerun, like a failed `git init`, and the run exits 0. A step that did not run (`--no-install`) or failed is listed in the summary's next steps, after the dependency install (`PendingPostGenerateStep`), and a step the CLI could not run for lack of an install is also in the Getting Started of the README (`manualPostGenerateSteps`). A formatter must leave alone the generated files that have to stay byte-identical to a tool's own output (the committed `src/routeTree.gen.ts`, and under Drizzle the `drizzle` migrations directory, whose `meta/*.json` drizzle-kit writes without a final newline): they are excluded through the ignore files of each formatter, never through a step.
  - `installScripts`: `Record<packageName, boolean>` on a stack, library, project addon or blueprint, naming the dependencies it brings (direct or transitive) that have an install script (`preinstall`, `install`, `postinstall`, an implicit `node-gyp rebuild`): `true` lets the script run, `false` skips it. `collectInstallScripts` merges the entries of the selected choices (`getAppLibraries` gives the libraries an app's stack supports), and a unit test fails when two entries rule differently on a package. The list follows the choices, so a project carries only what it installs; list a package on the choice whose dependency brings it, and name a ruling shared by several choices once (`TSX_INSTALL_SCRIPTS`, `WRANGLER_INSTALL_SCRIPTS` in `__meta__.ts`). See Install scripts of dependencies.
  - Category-level and addon-level `require`. `require.stacks` requires at least one app on a listed stack (for example `cloudflare-static` requires a Next.js or TanStack Start app; a turborepo mixing it with an unsupported stack still passes, and that app gets no `wrangler.jsonc`).
- **`$when` conditions** (`apps/cli/src/lib/when.ts`, wrapping package.json values and array items in `__meta__.ts`): keys `repo`, `pm` (the effective package manager, `npm` when none is selected, as for the printed commands), `stack`, `library` and any `ProjectContext` category (`database`, `orm`, `deployment`, `linter`, `tooling`). The value is a string, a list (any-of) or `true` (the category has a selection). Every key accepts a negation, `{ not: <value> }`, true when the positive match is false: `$when({ deployment: { not: 'cloudflare' } }, ...)` or `$when({ deployment: { not: ['cloudflare', 'cloudflare-static'] } }, ...)`. An unselected category satisfies any `not` (`{ not: 'cloudflare' }` is true when no deployment is chosen; `{ not: true }` is true only when the category is unselected). `stack` and `library` follow any-app semantics (`{ not: 'nextjs' }` is true only when no app uses Next.js). All keys of one `$when` must hold.
- **package.json script placeholders** (resolved by `resolveScriptPlaceholders` in `addon-utils.ts`, applied to the scripts of every generated package.json; `{{port}}` is resolved earlier by `processScriptPorts` in `utils.ts`): `{{port}}` (the port of the app: 3000 plus its index in a turborepo, 3000 in a single repo, which has one app; in a single repo only the flag `--port {{port}}` is removed, so the runtime takes its own default (see Changing the port of an app), in a turborepo the flag becomes `--port ${PORT:-3001}` so a `PORT` in the environment wins, and every other `{{port}}` of a script, such as `${PORT:-{{port}}}`, resolves to the port of the app. A script carries it so the app has a URL: `usesPortPlaceholder` is what makes `appUrl` non-empty), `{{workspaceRoot}}` (repo-relative path to the workspace root: `.` in a single repo, `../..` in a turborepo) and `{{deployAppDir}}` (directory name of the app that consumes the deployment binding: the deployment's `stackPackageJson` stacks, preferring an app with a `needsSingletonDb` library; resolved by `resolveDeployAppDir`). Two more tokens follow the package manager: `{{packageManager}}` (`bun`, `npm` or `pnpm`, for a script that re-enters a script from another directory: `cd {{workspaceRoot}} && {{packageManager}} run db:seed`) and `{{tsRunner}}` (as the Handlebars helper). Author topology-dependent script strings with these tokens in META and combine them with `deploymentPackageJson` + `$when` for repo and deployment splits; never compute app paths in the generator. For example the d1 turborepo migrate script is `wrangler --config {{workspaceRoot}}/apps/{{deployAppDir}}/wrangler.jsonc d1 migrations apply DB --local --persist-to {{workspaceRoot}}/.wrangler`.

When you need choice-conditional behavior and no operator covers it, the correct move is to add a new generic operator (a Handlebars helper or a frontmatter key handled generically by the resolver) and document it in this file under Template system, never to special-case a value in core code. Generalize first, then use it.

Compatibility and capability data is a separate mechanism: it is declared as META fields and read by generic checks (see META capabilities), never as a branch on a value in core code.

This keeps the tool extensible: adding the next stack, library or deployment requires a META entry and templates, never an edit to a core algorithm.

## META capabilities

`META` (`apps/cli/src/__meta__.ts`) has `stacks`, `libraries`, `project` (categories `database`, `orm`, `deployment`, `linter`, `tooling`), `repo` and `blueprints`. The lists of choices, the stacks each library supports (`support.stacks`) and the requirements live there; read them instead of copying them into docs or code.

- `META.stacks`: `type: 'app' | 'server'`, label, base `packageJson` and `productionScripts`.
- `productionScripts`: `Conditional<ScriptDescription>[]` on a stack or a project addon, where `ScriptDescription` is `{ script, description }`: the package.json scripts that build, serve or ship an app, with the sentence the READMEs, `AGENTS.md` and the CLI summary give them, in the order a user runs them (`collectProductionSteps` concatenates the stack of the app, then the selected addons, and keeps the first entry of each script, for each app and for the project; so declare a script after the ones it needs: an addon's `build:cf` before its `preview`). Declare the script on the stack or addon that defines it; an entry for a script a project does not define is skipped, so a deployment lists `build:cf` once for every stack it supports. A sentence that changes with the repo type is a `$when` item (`describedPerRepo` in `__meta__.ts`: a turborepo root runs `build` and `start` in every app that defines them: a Hono app on Bun and an Expo app have no `build`, so the sentence says "every app that has a `build` script"). The description must fit the script (Expo's `start` is its dev server). Read generically, never as a branch on a stack or deployment.
- `scriptDescriptions`: `Conditional<ScriptDescription>[]` on a stack, a library, a project addon, a blueprint and a repo type (`META.repo.stacks`, for the scripts the generated root `package.json` defines on its own: `clean`, `versions:list`, `versions:fix`), the sentence of every root script that is not a production script (a repo type also declares the scripts themselves in its `packageJson`: the turborepo root `clean` and `versions:*` are read from `META.repo.stacks.turborepo`). Declare it on the choice whose `packageJson` declares the script (`dev` and `analyze` on the stacks, `test` on `vitest`, `lint` and `format` on each linter, `db:push` on each ORM, `local-setup` on `d1` and on the blueprints that ship their own), with a `$when` item for a sentence that changes with the repo type (`START_DEV_SERVER`). `ScriptDescription` is the shape of `productionScripts` plus an optional `readmeSection`, the README section that explains the script, which the list points to ("see Seeding below" in the README, "see Seeding in the README" in `AGENTS.md`). A script has one sentence: a production script is described by `productionScripts` only, never also by `scriptDescriptions`, and the choices that declare the same script (`db:generate` on `d1` and `drizzle`, `lint` on three linters, `local-setup` on `d1` and a blueprint) share one constant. `collectScriptList` lists, in this order, the scripts the stacks describe, the interactive and production steps, then the scripts of the libraries, the project addons (in the order of `META.project`), the blueprint and the repo type, each script once, the first declaration winning, and the scripts of the libraries, addons, blueprint and repo type that share the name before the first `:` (`db:push`, `db:seed`, `local-setup` apart) kept together at the place of the first; a `scriptDescriptions` entry for a script the project does not define is skipped. `tests/unit/lib/script-list.test.ts` fails, naming the combination and the script, when a root script that a stack, a library, a project addon, a blueprint or the repo type generates has no sentence, when a script is described by both fields, and when two choices give one script two sentences. A new root script is a `scriptDescriptions` entry, never an edit to the `scripts/root-list` partial.
- `interactiveScripts` on a stack: the scripts of an app that need a terminal, which turbo's stream UI never gives a task (Expo prints no QR code and takes no key press without one). The stack names them, and defines them under a name the turborepo root does not forward through turbo (`dev` and `start` are, in every app that has them): Expo's is `dev:expo`, under `$when({ repo: 'turborepo' })` (a single repo runs no turbo, so Expo keeps `dev`). `collectInteractiveSteps` prints one step per app that has the script and the root does not, with a sentence that names no stack (`Run dev:expo in a terminal of its own (mobile)`), as `(cd apps/mobile && bun run dev:expo)` through `getScriptCommandInApp`; it shares `appOnlyScriptSteps` (`lib/production-steps.ts`) with the production steps. A unit test fails when an app of a stack that declares interactive scripts defines one the turborepo root forwards through turbo (the root scripts that are `turbo <name>`, `dev` included), and when no stack declares any. For the scripts of an ORM or a database see Database first run.
- `pinnedPackages: string[]` on a stack or a library: the packages it needs at the version it declares (Expo's `react` and `react-dom`, which React Native checks against its renderer, and `@types/react`, whose minor `expo-doctor` checks; NativeWind's `tailwindcss` 3), whatever the other apps of a turborepo use. Each must be in the `dependencies` or `devDependencies` of the same choice (unit test). `collectSyncpackConfig` turns them into one ignored syncpack version group per app, so `versions:list` accepts the difference and `versions:fix` never moves it; see Versions across the workspaces. A package that merely drifted is not pinned: it takes the shared constant.
- `META.libraries`: per-app addons with category, `support`, `require`, `mono`, `packageJson`, `stackPackageJson`, `envs`.
- `META.project`: each category declares its prompt, `selection: 'single' | 'multi'`, an optional category-level `require` (an ORM requires a database) and its `options`, which are addons like libraries.
- `META.blueprints`: preset context (apps with their libraries, plus `database`, `orm` and `deployment`), extra `packageJson` and `envs` for every app, an optional `packageJson`, `envs` and `installScripts` on each app of `context.apps` for what only that app receives (see Blueprint apps), an optional `extends` (the name of a parent blueprint whose templates it inherits, see Template system, `extends`), and an optional `agentArchitecture` text for the generated `AGENTS.md`.
- Blueprint seed: a blueprint that ships its own seed script (a template at a seed destination, `scripts/seed.ts`, in its chain) declares what it does to existing data in `seed` (`BlueprintSeed`, a union): `rows` names what it empties as the docs say it (`contacts`, `users`), and `deletes` is `always` (before every run, no `target`: it runs against `DATABASE_URL` whatever it is) or `with-reset` (only with `--reset`, which also gives the seed `--fixtures` and `--help`), the latter with a `target`: `local-only` (it opens the local database and nothing else) or `refuses-remote-without-force` (`--reset` refuses a database that does not look local unless `--force` is passed). `never` is a seed that only adds what is missing and deletes nothing (`cloudflare-payload-nextjs`): `rows` then names what it adds, and the `seed/blueprint` partial says so. Any variant may carry `file`, where the seed lives when it is not the `scripts/seed.ts` of the root (`apps/web/scripts/seed.ts`, run by `payload run`, which loads the `.env` of the app itself); the `seedFile` helper and `blueprint-seed-docs.test.ts` read it. The type allows no other combination, so the sentence of each is written once. `seed` is not inherited through `extends`: `org-dashboard-tanstack-start` declares it too, from the shared `ORG_DASHBOARD_SEED`. The `seed/blueprint` partial branches on each case and renders the exact sentence for the README `## Seeding` section and for the `data-layer.md` of the blueprint, so a new seed behavior is a variant of the type and a branch in that one partial, never a sentence written in a guide. A blueprint without its own seed (rainbowkit) declares none and its docs say what the ORM seed does (`seed/deletes-users`). `tests/unit/lib/blueprint-seed.test.ts` fails when a blueprint ships a seed template without declaring `seed` (or declares one without shipping it), and `tests/integration/blueprint-seed-docs.test.ts` generates each seeding blueprint, with and without `--no-agent-context`, checks the README and guide sentence, and checks the data against the generated `scripts/seed.ts` (the `--reset`, `--fixtures`, `--help` and `--force` flags, the refusal message, the local database signal and the tables it deletes).
- `generatedFiles: GeneratedFile[]` on a stack, a library, a project addon (an ORM, a linter) or a blueprint: the committed files its tools write, which every linter and formatter ignores (`**/routeTree.gen.ts` on `tanstack-start`, `**/drizzle/**` on the `drizzle` ORM, `**/src/payload-types.ts`, `**/importMap.js` and `**/src/migrations/*` on `cloudflare-payload-nextjs`). A `GeneratedFile` is a glob that every tool reads the same way (a string), or `{ glob, as }` where `as` gives the form one tool reads (Biome and oxfmt read `**/drizzle/**/*`, Prettier `drizzle/`) or `false` when that tool already ignores the file (ESLint and oxlint skip `routeTree.gen.ts`). `collectGeneratedFiles` (`lib/generated-files.ts`) collects the patterns of the selected choices for one tool, read by the `generatedFiles` helper (see Template system, Handlebars helpers). A glob that names a folder ends in `/*`, not `/**`: Biome warns about the latter. `tests/integration/linter-ignores.test.ts` checks that each linter lists the files of Payload and that the patterns match them, `tests/unit/lib/generated-files.test.ts` the collector, and `tests/e2e/blueprint-cloudflare-payload-nextjs.test.ts` that `generate:types` and `generate:importmap` rewrite the committed files with the same bytes.
- Addon `require` (`AddonRequire`): `git`, `linter`, `database`, `orm`, `deployment`, `tooling`, `libraries`, `stacks`. A flag or prompt that violates it is rejected generically (`isRequirementMet`, `describeRequire`).
- Server-runtime capability: a library declares `needsServerRuntime: true`; a deployment declares `providesServerRuntime: false` for static-only targets. Read generically by `isServerRuntimeSatisfied`: a server-less deployment is unavailable when any selected library needs a runtime.
- Singleton-db capability: a database declares `serverlessBinding` (it is accessed per request through a Cloudflare binding, no module singleton; `d1`, and `postgres` and `mysql` through Hyperdrive); a deployment declares `providesDbBindings: true` (Cloudflare); a library declares `needsSingletonDb: true` (better-auth, trpc consume a module-singleton `db`). A binding database whose server-side consumers are wired per request declares `serverlessConsumersWired: true` (`d1`). Read generically by `isSingletonDbSatisfied`: a binding-based database under a binding-providing deployment is unavailable when any selected library needs a singleton db, unless its consumers are wired. D1 is wired: better-auth and trpc build per request through `getDb()` and `getAuth()` from the app-side `src/lib/server.ts` (`templates/project/deployment/cloudflare/src/lib/server.ts.{nextjs,tanstack-start}.hbs`), gated by `{{#if (has "database" "d1")}}` in the `auth` and `trpc` templates. `postgres` and `mysql` on Cloudflare stay disabled with better-auth and trpc until their consumers are wired too.
- Local-filesystem capability: a database declares `needsLocalFilesystem: true` (`sqlite` opens a `file:` URL); a deployment declares `providesLocalFilesystem: false` when its runtime has no persistent writable disk (`cloudflare`, Workers; `sst` and `terraform-aws`, Lambda). Read generically by `isLocalFilesystemSatisfied`: a filesystem database is unavailable under a deployment without one (`d1` is the SQLite database there). `validateContext` rejects it in flags and `getCategoryOptionUnavailability` disables it in the prompt.
- Client-only capability: a stack declares `clientOnly: true` when its app runs on a device and never runs server code (`expo`); the `database` and `orm` categories of `META.project` declare `serverOnly: true` because their client runs in server code. Read generically by `appReceives` (`addon-utils.ts`): in a turborepo an app on a `clientOnly` stack receives nothing a `serverOnly` category brings, so it has no `@repo/db` dependency and no database `stackPackageJson` (`composeApp`) and none of the database variables (`appAcceptsEnv` in `env-generator`, which every `.env.example`, README and `AGENTS.md` env list, `appSecrets` and the first-run steps share; a `{ pkg }` or root variable is written when at least one app receives it). A single repo has one app, which owns the project tooling (the `db:*` scripts, the config and seed files), so it keeps the dependencies and the variables whatever its stack. The flags are not a compatibility check: they do not reject a project whose apps are all client-only. The turborepo README prints no per-app line about the database package, because only some apps depend on it.
- Single-select project prompts show incompatibility instead of hiding it: `getCategoryOptionUnavailability` (`addon-utils.ts`) returns a generic, META-derived reason for any option, and `promptProjectCategorySingle` renders unavailable options disabled with that reason. No hardcoded choice value.

### Install scripts of dependencies

npm 12 and pnpm 11 and later do not run a dependency's install script unless the project allows it: npm 12 warns and skips, pnpm 11 and 12 fail the install with `ERR_PNPM_IGNORED_BUILDS`; npm 11 runs the script and prints a notice, pnpm 10 skips it and prints a warning. Every dependency of a generated project with such a script is therefore ruled on in META (`installScripts`), and the rendering follows the effective package manager (`getInstallScriptsField` in `lib/package-manager.ts` for the manifest field, the `pnpm/allow-builds` partial for pnpm):
- npm (also when none is selected): `allowScripts` in the root `package.json` (the single app, or the turborepo root: npm ignores the field in a workspace and warns). Older npm ignores the unknown field.
- pnpm: `allowBuilds` in `pnpm-workspace.yaml` (pnpm 10.26 and later, 11, 12; older pnpm ignores it, pnpm 10.0 to 10.25 keeps its warning). `repo/turborepo/pnpm-workspace.yaml.hbs` adds it to the workspace declaration; `repo/single/pnpm-workspace.yaml.hbs` exists only when a dependency has to be ruled on, with `packages: [.]` because pnpm 9 rejects a workspace file with no `packages`. The `onlyBuiltDependencies` family is removed in pnpm 11 and the `pnpm` field of `package.json` is no longer read.
- bun: nothing. Bun blocks the scripts of untrusted dependencies and trusts a built-in list (`esbuild`, `workerd`, `prisma`, `@prisma/engines`, ...); a `trustedDependencies` field replaces that list, so declaring one would block what bun runs today. The only package left blocked is `core-js` (`posthog`), which prints `Blocked 1 postinstall` and costs nothing.

The rule for a package is whether the project works without the script. `esbuild` and `workerd` swap their JS shim for the binary of the `@esbuild/*` or `@cloudflare/workerd-*` optional dependency (an optimization, and a download fallback only when optional dependencies are off); `fsevents` rebuilds from source a macOS file watcher that ships prebuilt; `core-js` prints a donation notice; `prisma` checks the Node version; `bufferutil`, `utf-8-validate` and `keccak` are optional native speedups with JavaScript fallbacks: all `false`. `@prisma/engines` downloads the schema engine that `prisma db push` and `migrate` run (Prisma would fetch it on first use otherwise, which fails offline): `true`. `tests/integration/install-scripts.test.ts` generates a project per META entry that rules and checks the rendering, and the inventory is in `docs/agents/install-scripts/inventory.md`.

`tests/e2e/install-scripts.test.ts` is the guard for a dependency added without a ruling: it installs every library on each stack it supports and every project option, packed first-fit into a few projects by their requirements (`tests/choice-projects.ts`, shared with `tests/integration/app-scope.test.ts` and `tests/integration/syncpack.test.ts`, so a new choice is covered without an edit), plus every blueprint, with pnpm in its strict mode (pnpm 11 or later, fetched with `npx pnpm@12` when the installed one is older) and fails naming each `Ignored build scripts` package. Run it on demand (`cd apps/cli && bun test tests/e2e/install-scripts.test.ts --timeout 600000`) after a dependency bump or a new choice, and in the release check. A package that is unruled only on another OS (`fsevents` on macOS) is not seen on Linux: rule the optional native dependencies of a watcher explicitly. A failure is fixed by adding the package to the `installScripts` of the choice that brings it (`npm install-scripts ls` under npm 12 lists the same packages).

### Type check script

Every app and workspace package that has a `tsconfig.json` defines `typecheck` as `tsc --noEmit`: the five stacks and the packages `ui` (`shadcn`), `auth` (`better-auth`), `api` (`trpc`), `db` (both ORMs) and `shared` (the Lambda blueprints) declare it in META (`TYPECHECK_WITH_TSC`), so a single repo gets the same script on its app. A turborepo root forwards it as `turbo typecheck` through `APP_SCRIPTS_RUN_BY_TURBO`, like `build`, so the root script exists when an app defines it, and `turbo.json.hbs` declares the task under `hasRootScript "typecheck"` with `dependsOn: ["^typecheck"]`, so a change in a package invalidates the type check of the apps that use it (a task that depends on nothing would stay cached while the code it imports changed). With Prisma the task also depends on the `db:generate` of its own package, because the client is generated and not committed, and a single repo declares `pretypecheck: prisma generate` the way it declares `predev` and `prebuild`, all three from `PRISMA_GENERATE_IN_SINGLE_REPO` in META. The sentence is `TYPECHECK_CODE` on the stacks (`scriptDescriptions`, one per repo type); a new workspace package with a tsconfig declares `TYPECHECK_WITH_TSC` (`tests/integration/typecheck-script.test.ts` fails, naming the workspace, when one does not).

### Database first run

Turbo's `ui: stream` never forwards stdin, so a script that prompts hangs behind an invisible prompt (`prisma migrate dev` asks for a migration name) or fails while turbo still reports success (`drizzle-kit push` asks for confirmation and aborts without a TTY). An ORM declares such scripts in `interactiveScripts` (Drizzle `db:push`, Prisma `db:migrate`); `composeRootPackageJson` writes their turborepo root script as `cd packages/<db> && <pm> run <script>` instead of `turbo <script>`. A blueprint `rootPackageJson` must not redefine the `db:*` scripts the ORM already provides. A database declares them too (`d1`: `db:migrate:remote` asks Wrangler's confirmation); the turborepo root then exposes them as `cd packages/<db> && <pm> run <script>` like the ORM ones.

The `d1` option without an ORM generates no script and no dependency of the Drizzle workflow: `db:generate` (`drizzle-kit`), `db:migrate`, `db:migrate:local`, `db:migrate:remote` (Wrangler `d1 migrations apply`, whose migrations directory only an ORM writes), `local-setup` (which calls `db:seed`) and the `@libsql/client` devDependency are `$when({ orm: true })` in META, in a single repo and in a turborepo alike (in a turborepo they only reach `packages/db`, which exists with an ORM). Their `scriptDescriptions` stay on the option: a sentence for a script the project does not define is skipped. The `wrangler.jsonc` binding carries `migrations_dir` only with an ORM, `.env.d1.example` is written only with an ORM, and `src/lib/server.ts` (the `db` and `getDb()` of the Cloudflare fiche) exists only with an ORM; the Cloudflare fiche describes it under the same condition, and its note on the shared `.wrangler/` directory names the `db:migrate` script only when the root defines it. The provisioning steps follow these scripts (see Cloudflare, D1 provisioning). `tests/unit/lib/d1-without-orm.test.ts` and `tests/integration/d1-without-orm.test.ts` generate it for both repo types and the three server stacks.

The Prisma client is generated into `generated/prisma` and not committed, and `prisma generate` reads `DATABASE_URL` through `prisma.config.ts`, so it cannot be a `postinstall` (the install runs before `.env` exists). It runs before `dev` and `build` instead: `repo/turborepo/turbo.json.hbs` adds `^db:generate` to both under `has "orm" "prisma"` and caches `generated/**`; in a single repo the Prisma ORM scripts define `predev` through `$when({ repo: 'single' })` and `prebuild` the same way on the stacks that define `build` (`STACKS_WITH_BUILD_SCRIPT`: a hook of a script the app lacks would never run). Drizzle `db:generate` writes migration files into the source tree, so its task has `cache: false`.

The first-run steps are META data (`firstRun` on a project addon or a blueprint, see below), so the README and the CLI summary cannot drift. The commands never prompt: `docker compose up -d --wait` for a Docker database (`postgres`, `mysql`), then `db:generate` and `db:push` for Prisma (`prisma db push` does not generate the client, which `db:seed` and `tsc` need), or `db:generate` then `db:migrate` for Drizzle (every database, D1 included). The template ships no migration, so `db:migrate` alone has nothing to apply. The `local-setup` script of D1 runs `db:generate` first for the same reason.

### First-run steps

`firstRun` (`FirstRunStep[]`: a `description` and `commands`, each `{ script }` run through the selected package manager like `runScript`, or `{ command }` written as is) is declared on a project addon (a Docker database, an ORM) or on a blueprint. `collectFirstRunSteps` (`lib/first-run.ts`) returns the ordered steps of a project: the env files to copy (derived from `collectEnvGroups`, no META needed), a step per variable that declares `generateCommand` (see `envs` `generateCommand`; kept when a blueprint replaces the addon steps), then the `firstRun` of the selected addons in the order of the `META.project` categories. A blueprint `firstRun` replaces the addon steps (a blueprint with its own `local-setup` script declares it), the env step stays. The `firstRunSteps` Handlebars helper exposes the same list to the `readme/first-run` partial (the Getting Started section of both repo READMEs), and `buildStepsNote` in `tui/summary.ts` prints it before `dev`. Adding a database, ORM or blueprint with a first-run command is a META entry, never an edit to either consumer.

### Database TLS in production

A generated client reaching a Docker database through `DATABASE_URL` connects with TLS and certificate verification when `NODE_ENV=production`, and the local `.env.example` URL opts out, so a production build still runs against the local Docker database.
- PostgreSQL: the URL ends with `?sslmode=disable`; the Drizzle and Prisma clients set `ssl: process.env.NODE_ENV === 'production'`, which pg overrides with the parsed `sslmode`.
- MySQL: the URL ends with `?ssl=false`, which both `mysql2` (Drizzle) and the MariaDB connector behind Prisma's adapter read as no TLS. Neither driver lets code options default TLS on under a URL parameter (`mysql2` keeps a truthy code `ssl` over the URL), and the value that turns TLS on differs (`ssl={}` for `mysql2`, which rejects `true`; `ssl=true` for the connector, which reads `{}` as no TLS), so the `mysql/production-tls` partial appends `ssl=<tlsValue>` to the URL in production when it carries no `ssl`.
- Both clients log one warning in production when the URL disables TLS for a host other than localhost (`postgres/tls-warning`, `mysql/production-tls`). A Cloudflare Hyperdrive client has none: the binding carries the connection.
- The generated `AGENTS.md` of each database says where `NODE_ENV=production` comes from for the project's stacks (`database/node-env-production`, shared). A new database that connects with a URL does the same: TLS on in production by default, one URL parameter for the local opt out, a test like `tests/integration/postgres-ssl.test.ts` and an e2e against a real container (`tests/e2e/postgres-production.test.ts`, `tests/e2e/mysql-production.test.ts`).

### Scripts that run under every package manager

A script a generated project ships (a package.json script, `scripts/*.ts`) runs under Node for npm and pnpm and under Bun for bun, so no template calls a Bun API (`Bun.spawn`, `Bun.Glob`, `bun:sqlite`), starts with a `#!/usr/bin/env bun` shebang, or writes `bun run ...`.
- A `.ts` file is run through the `{{tsRunner}}` token (`bun`, or `tsx` for npm and pnpm). `tsx` is a devDependency of the package that runs it, declared with `TSX_RUNNER` (`$when({ pm: { not: 'bun' } })`). It runs the file as CommonJS when the package has no `"type": "module"`, so a script avoids top-level `await`.
- A script that calls another script writes `{{packageManager}} run <script>`, never `bun run --cwd` (`cd {{workspaceRoot}} && {{packageManager}} run db:seed`).
- The command a script prints or runs (`sh` in the blueprint `local-setup.ts`, the usage text of a seed) comes from `{{runScript "name" "args"}}`, resolved when the project is generated. `args` carries the `--` npm needs to forward flags.
- `scripts/local-setup.ts` of the blueprints shares `partials/local-setup/steps.hbs`: `node:child_process` `spawn` with a shell, a directory walk for `.env.example` files, no glob dependency. Its closing message names no account or password: the seed prints the accounts with the password it used (`SEED_PASSWORD`), so a literal one in the message would be wrong as soon as it is set.
- A seed reads its environment itself, unconditionally (it always needs its database URL or the demo password): `import 'dotenv/config'` as the first import of the generic Drizzle seed (every database, D1 included; Bun loads `.env` on its own, Node does not) and of the single-repo `dapp-privy-nextjs` seed that replaces it, or `--env-file=apps/web/.env` on the root `db:seed` script of a turborepo blueprint (the seed runs from the root, the `.env` sits in the app; the flag is `--env-file`, never `--env-file-if-exists`, which Bun ignores and would load nothing, so Node exits 9 when the `.env` the first-run steps create is missing). Prisma loads it through `prisma.config.ts`, whose first import is `dotenv/config`. `tests/integration/seed-environment.test.ts` generates every blueprint and the generic seeds under npm, follows each `db:seed` (a `cd .. && <pm> run db:seed` or `turbo db:seed` forward included) to the file `tsx` or `node` runs, whatever its extension, and fails when that file neither is run with an `--env-file` flag whose target has an `.env.example` beside it nor starts with `import 'dotenv/config'`.
- A seed for the local D1 database opens the miniflare file with `@libsql/client` and `drizzle-orm/libsql` (the same on both runtimes), never `bun:sqlite`.

- The `hono` and `node` stacks and the two Lambda blueprints declare the Bun version in `packageJson` and the npm and pnpm one in `packageManagerPackageJson` (a `Partial<Record<pm, PackageJsonConfig>>` on a stack or a blueprint, merged right after it when the effective package manager matches). A Hono app on npm or pnpm gets `src/server.ts` (empty-render skipped under bun, and `deploymentSkip: [cloudflare]`: a Worker has no Node server, see Cloudflare): `@hono/node-server` serves `app` of `src/index.ts`, which keeps its default export for Bun, Workers and Lambda; the port is `PORT`, else the `--port {{port}}` flag the script carries (stripped in a single repo and by portless, like the Bun flag). The Lambda `build` is `esbuild` (an explicit devDependency, ES module bundle for `node22` with a `require` banner); the `lambda-terraform-aws-hono` build adds `--define:process.env.NODE_ENV=\"production\"` (backslash-escaped quotes: `sh`, which runs the scripts under npm and pnpm, strips a bare `"production"` and esbuild then reads an identifier, a ReferenceError at runtime; `tests/integration/lambda-build-quoting.test.ts` splits every generated script that carries a `--define:` through `sh` and requires each value to be a JSON literal), as `NODE_ENV=production bun build` inlined it, and the deploy workflows set Bun up only under bun.
- The URL the README prints for an app that listens (`appUrl`, `Open [..] in your browser`) answers for every stack: the Hono `src/app.ts` serves a JSON status on `GET /` next to the sample `/health/:id` route, so the link is not a 404 (`tests/integration/hono-app.test.ts`). The README prints no per-stack path, because a link path would be a new META field read by the README and by the summary.

### Prompts, testing libraries and linters

- Library prompts group libraries by their `category` field (`UI`, `Content`, `Auth`, `API`, `Data Fetching`, `Forms`, `Runtime`, `Observability`, `Analytics`, `Testing`); `multiselectLibrariesPrompt` in `prompts/stack-prompts.ts` builds the groups from META.
- Testing libraries: `vitest` (Next.js, TanStack Start; jsdom and Testing Library) and `vitest-node` (Hono, Node) declare the scripts `test`, `test:watch`, `test:coverage`; `playwright` (Next.js, TanStack Start, app-scoped config) declares `test:e2e` and `test:e2e:ui`; `jest-expo` (Expo, `jest-expo` preset and React Native Testing Library) declares `test` and `test:watch`.
- Generated and build output is never linted: a generated project must pass its own `lint` script before and after its `build`, for every linter (`tests/e2e/generated-lint.test.ts`). Biome reads the generated `.gitignore` (`vcs.useIgnoreFile`), so a build directory a choice writes only needs its `.gitignore` section; `biome.json.hbs` lists only the generated files that are committed (`routeTree.gen.ts`). The ESLint configs keep explicit ignore lists that mirror those `.gitignore` sections (the `eslint/cloudflare-ignores` partial holds the Cloudflare entries). oxlint, oxfmt and Prettier read `.gitignore` too, and `oxfmt.config.mts.hbs` and `__prettierignore.hbs` add the committed route tree. A new build directory goes in the `.gitignore` section and in the ESLint ignores of its choice.
- A generated project prints no lint warning either, whatever the linter: the same e2e runs the `lint` script with the flag that makes the linter fail on a warning (`FAIL_ON_WARNINGS_FLAGS`: Biome `--error-on-warnings`, oxlint `--deny-warnings`, ESLint `--max-warnings 0`). The `lint` script of an ESLint turborepo is `turbo lint`, which forwards no flag, so the e2e runs the script of each workspace that calls the linter itself. A new linter that can fail on a warning gets its flag there. A rule a template trips is fixed in the template (an environment read that must exist throws a clear error, never `process.env.X!`). A file copied verbatim from the shadcn registry is not rewritten: `biome.json.hbs` overrides the rule for that file under `hasLibrary "shadcn"`. Biome's `noUndeclaredEnvVars` warns on a root-package file (a blueprint `scripts/seed.ts`) that reads a variable `turbo.json` does not declare, and skips `packages/*`: declare what a task reads with `tasks` in META (see `envs` `tasks`).
- ESLint in a turborepo lints the workspace packages through the root `lint` (`turbo lint`), which only reaches the workspaces that define a `lint` script. Biome and oxlint lint from the root and exclude no `packages/**` path (`tests/integration/eslint-workspace-packages.test.ts` checks both). Each workspace package with sources has an `eslint.config.mjs` and `"lint": "eslint ."`, like an app. META is the only place the script and the `eslint` and `@repo/eslint-config` devDependencies are declared: a package that comes from META (`ui`, `auth`, `api`, `db` for Drizzle and Prisma, `shared` of the Lambda blueprints through their shared `LAMBDA_PKG_PACKAGE_JSON`) passes its `packageJson` or `pkgPackageJson` through `lintsWithEslint(...)` in `__meta__.ts`, which adds the four fields from one place (the `lint` script `eslint .`, the `eslint` and `@repo/eslint-config` devDependencies and the `lint-staged` entry `ESLINT_STAGED_IN_WORKSPACE`), all under `$when({ repo: 'turborepo', linter: ['eslint', 'eslint-prettier'] }, ...)` so a single repo and the other linters get none, and the `eslint` addon gives `eslint-config` its own `lint`. The config file is one template per package in `templates/project/linter/eslint/` (`<package>-eslint.config.mjs.hbs`, `mono: { scope: pkg, name: <package>, path: eslint.config.mjs }`, wrapped in `{{#if (hasPackage "<package>")}}` so it is skipped when the package is not generated). The app configs of a turborepo (`eslint.config.mjs.<stack>.hbs`) and these package ones all render the `eslint/workspace-config` partial, which holds the shape of the file (import a preset of `@repo/eslint-config`, export it as default) and takes `config` and `from`; the preset is `serverConfig`, or `reactConfig` for `ui`. Adding a package therefore means passing its META config through `lintsWithEslint` and adding its `<package>-eslint.config.mjs.hbs` template; the integration test fails, naming the package, when a generated package with sources has no eslint `lint` script, no `eslint.config.mjs` or no `eslint` devDependency. Linting the packages makes the shared presets cover third-party and vendored files, which are not rewritten, so overrides are declared once: `base.js` ignores `generated/**` (the Prisma client of `packages/db`) and sets `ignoreRestSiblings` on `@typescript-eslint/no-unused-vars` (the omit-by-destructuring idiom); the `react` preset, under `hasLibrary "shadcn"`, turns `react-hooks/purity` off for the shadcn `sidebar.tsx` (as `biome.json.hbs` does for its rule) and `react-hooks/set-state-in-effect`, `react-hooks/refs`, `react-hooks/incompatible-library` and `@typescript-eslint/no-unused-vars` off for the vendored `**/shuip/**` components (a glob that matches nothing costs nothing).
- ESLint in a turborepo with `husky` runs `eslint --fix` on the staged files in each workspace, never at the root. ESLint 9 looks its config up from the directory it runs in, and the root has no `eslint.config.*` (and, under bun, no `eslint` binary), so a root `lint-staged` entry fails for every staged file. lint-staged uses the closest config of each staged file and runs its tasks in the directory of that config (the same behavior a monorepo relies on), so every workspace that lints itself (an app, `eslint-config`, and each package) carries a `lint-staged` key in its `package.json`: `ESLINT_STAGED_IN_WORKSPACE` in `__meta__.ts`, added to the packages by `lintsWithEslint` and set directly in the `eslint` addon (`packageJson` for `eslint-config`, `appPackageJson` for the apps), under `$when({ repo: 'turborepo', linter: ['eslint', 'eslint-prettier'], tooling: 'husky' }, ...)`. lint-staged runs the tasks in the directory of the config only when the project has more than one lint-staged config (`hasMultipleConfigs` in its `runAll.js`), which a turborepo with the entries above always has. lint-staged does not merge configs, so `eslint-prettier` repeats `prettier --write` there (`prettier` is a root dependency, found from the workspace directory); the root `husky` entry keeps `eslint --fix` only for a single repo (`repo: 'single'`) and `prettier --write` for the prettier linters. Not used: ESLint's `--flag unstable_config_lookup_from_file`, renamed `v10_config_lookup_from_file` in ESLint 9.39 (the old name only warns), so a command with either name depends on which 9.x the install resolves, and it needs `eslint` at the root. A new package that lints itself goes through `lintsWithEslint`; `tests/integration/eslint-lint-staged.test.ts` fails, naming the workspace, when a staged source of a workspace with an `eslint` lint script has no `eslint --fix` task in its closest `lint-staged` config or no ESLint config at or above the directory the task runs in, and `tests/e2e/husky-hooks.test.ts` commits in a generated turborepo under bun, npm and pnpm (a clean app file and package file pass, a lint error blocks the commit with ESLint's message).
- Linter `oxc` generates a root `oxlint.config.mts` and `oxfmt.config.mts` (`templates/project/linter/oxc/`). `oxlint.config.mts.hbs` has one override per app that has a React stack or a test library, with native plugins chosen by stack and library, and the `@shadcn/lint` JS plugin for an app that uses shadcn. The plugin reads the classes Tailwind knows from the `tailwind.css` of the app's `components.json` and the stylesheets it imports: a single repo's `globals.css` imports `mdx.css`, but a turborepo app reads `packages/ui/src/base.css`, which does not, so the override of a turborepo app with `mdx` passes `allow: ['*-mdx']` to `shadcn/no-unknown-classes` for the `*-mdx` classes of `mdx-components.tsx` (`tests/e2e/oxc-lint.test.ts` lints that project). The cost is that a typo such as `h5-mdx` is not caught in a turborepo. A class an app declares in its own stylesheet needs the same, or a declaration in `base.css`.
- The `husky` tooling hooks are `pre-commit` (`lint-staged`) and `commit-msg`. `commit-msg` only warns: it checks the first line of the message against `<type>(<scope>): <subject>`, prints exactly one verdict (the valid line or the warning, never both) and always exits 0, so a message that is not conventional never blocks a commit made by a user who did not ask for the rule. The accepted types are written once, in the inline `husky/commit-types` partial, which the hook's pattern, the hook's warning list and the Husky fiche render. The first commit the summary suggests (`git commit -m "chore: initial commit"`, `tui/summary.ts`) passes it; `tests/integration/linter-tooling-fiches.test.ts` runs the generated hook on that message, on valid and invalid ones. A requirement error names only what is missing (`describeRequire(require, ctx)`: `--tooling husky` with `--linter` but no `--git` says `requires git`).

### MDX documents

A page of the `mdx` library never reads `contents/` with `fs` while it renders: a Worker has no such directory (`readdir '/bundle/contents'`), and OpenNext without an incremental cache (`defineCloudflareConfig({})`, the generated default) does not serve the prerendered HTML, it renders the route again for each request, so a read in the page or `generateMetadata` fails there even though `next build` passed. `generateStaticParams` runs at build time only, so it may list `contents/`. The documents themselves are compiled into the bundle, under every deployment: The one way to bundle `contents/` is `import.meta.glob` (Turbopack for Next.js, Vite for TanStack Start): lazy for the pages of the `mdx` library, eager for the blog of the two blueprints, which lists every post. `require.context`, a relative template-literal `import()` and `fs` are not used.
- Next.js: `@next/mdx` compiles each `.mdx` with `remark-frontmatter` and `remark-mdx-frontmatter` (named as strings in `next.config.ts.hbs`, which is what Turbopack accepts; the dependencies are on the library, shared with TanStack Start), so a document exports its YAML frontmatter as `frontmatter` (typed by `src/mdx.d.ts`; `MdxModule` in `src/lib/mdx.ts` is the shape of a document, on both stacks). `src/app/mdx/[[...slug]]/page.tsx` finds the documents with `import.meta.glob<MdxModule>('/contents/*.mdx')` (lazy, one chunk per document; the path is relative to the project root, which is the app directory in a turborepo) and maps a slug the glob does not hold to `notFound()`. A document added to `contents/` is served without editing the page. `generateStaticParams` lists the keys of the same glob, and `dynamicParams = false` makes Next.js answer 404 for a slug it does not list (`home`, a nested path, `constructor`, `..%2F`), before the page runs; `output: export` (`cloudflare-static`) still exports one page per document. `tests/integration/mdx.test.ts` fails when the page reads a file outside `generateStaticParams`, and `tests/e2e/nextjs-mdx.test.ts` serves a document added to `contents/` on `cloudflare`. `next dev` of Next.js 16.3 and later prints `MaxListenersExceededWarning` (11 close listeners on one `ServerResponse`) when it answers 404 for a slug that `dynamicParams = false` rejects and the project has the stack's proxy (`src/proxy.ts`, `src/middleware.ts` under `cloudflare`, none under `cloudflare-static`): the dev server runs the proxy twice for that request and Next.js 16.3 added one listener to its per-request budget (bare Next.js 16.4.2 with a proxy prints it, 16.2.12 does not; vercel/next.js#97757). The page keeps `dynamicParams = false` (`output: export` needs it) and the project raises no `maxListeners`; `tests/e2e/nextjs-modules.test.ts` marks the no-warning test `test.failing`, so it fails the day Next.js fixes it and the marker comes off.
- TanStack Start: `import.meta.glob('/contents/*.mdx')` in `src/lib/mdx.ts`, no `fs`.

### Better Auth and framework cookie plugins

Framework cookie plugins live in the app, in generic templates. The better-auth factory (`create-auth.ts` in a single repo, `packages/auth/src/auth.ts` in a turborepo, from `templates/libraries/better-auth/src/lib/auth/auth.ts.hbs`) has one shape per database, `createAuth(cookiePlugin?)` or `createAuth(db, cookiePlugin?)`. It knows no framework, appends the cookie plugin after its own plugins, and sets `session.disableSessionRefresh` when there is none (a refresh through an instance without a cookie plugin would extend the session in the database but lose the cookie).

Each app builds its instance from the factory with its framework's plugin: `src/lib/auth/auth.ts` (app-scoped `auth-instance.ts.hbs`, in a single repo and in every turborepo app) or `src/lib/server.ts` on D1. A Next.js app and a TanStack Start app can therefore share one auth package. Package-side consumers that cannot import an app instance (the tRPC package) use a cookie-less `createAuth()` for read-only session lookups.

Exception: a single-framework blueprint whose shared package calls cookie-setting endpoints (the `multitenant-saas-nextjs` routers call `changePassword` with `revokeOtherSessions`, `updateUser`, ...) may bind its framework's plugin in that package (`packages/api/src/auth.ts` calls `createAuth(nextCookies())`), because those cookies must reach the browser. That blueprint is Next.js only, so no other framework shares the package.

Production rate limiting keys on a client address header, which better-auth reads from `advanced.ipAddress.ipAddressHeaders` (default `x-forwarded-for`, which any client can set unless a proxy overwrites it). Every `betterAuth(...)` call (the library factory and the `org-dashboard-nextjs`, `multitenant-saas-nextjs`, `dapp-rainbowkit-nextjs` and `cloudflare-fullstack-nextjs` blueprint copies) inserts the `better-auth/client-ip` partial inside `advanced`: `cf-connecting-ip` under `cloudflare` (set by the edge, not spoofable through it), `x-forwarded-for` otherwise, with the generated better-auth notes describing the residual risk: better-auth rejects a multi-value `x-forwarded-for` (without `trustedProxies`), so an app exposed directly with no proxy can be dodged by rotating the header (it must sit behind a proxy or CDN that overwrites it), a single appending proxy is safe, and a proxy chain pushes every request into one shared bucket until `advanced.ipAddress.trustedProxies` is set. A new auth file calls the partial, never writes the header. A request that reaches the server with no `x-forwarded-for` would share one bucket with every other client, so the server fills the header with the connection address when it is absent, and leaves one a proxy set alone: `next start` does it itself (`req.headers['x-forwarded-for'] ??= socket.remoteAddress` in Next.js's `base-server.js`), and a TanStack Start app served by Nitro gets the same from `src/lib/nitro/client-ip.ts` (`templates/libraries/better-auth/src/lib/nitro/client-ip.ts.tanstack-start.hbs`), a Nitro plugin on the `request` hook reading `event.req.ip`, registered by `vite.config.ts.hbs` through `nitro({ plugins: [...] })` under `hasLibrary "better-auth"`. It is skipped on `cloudflare` and `cloudflare-static` (`deploymentSkip`), where `cf-connecting-ip` is trusted and there is no Nitro. A client that sends its own `x-forwarded-for` still picks its bucket when nothing in front of the app overwrites it. In e2e the probe in `tests/e2e/auth-probe.ts` plays the proxy or edge by setting a distinct address on both headers, and `expectRateLimitKeysOn` asserts that only the trusted one counts; `expectRateLimitKeysOnConnectionAddress` sends requests with no header from distinct loopback addresses and asserts one bucket per address, and that a header set by a proxy wins over the connection address.

### Mutation errors in the dashboards

A failed mutation tells the user why, and a better-auth refusal keeps its meaning on the way to the client.
- **Better Auth `APIError` to `TRPCError`, once.** With `better-auth` and `trpc` the library generates `auth-errors.ts` next to the tRPC instance (`src/trpc/auth-errors.ts`, `packages/api/src/auth-errors.ts` in a turborepo; empty-render skipped without better-auth). `trpcErrorFromAuthError` maps an `APIError` (matched by `name`, as better-auth's own `isAPIError` does, so the api package needs no better-auth dependency) to the tRPC code of its HTTP status with its message (400 `BAD_REQUEST`, 403 `FORBIDDEN`, 404 `NOT_FOUND`, ...; another 4xx is `BAD_REQUEST`, a 5xx stays `INTERNAL_SERVER_ERROR`). `init.ts` runs it in a middleware on `publicProcedure`, so every procedure of every blueprint (the SaaS routers included) inherits it. ### Post-login redirect

A login or signup form never passes a query parameter (`redirectTo`, `redirect`) straight to `router.push` or `redirect()`: an absolute URL would send a signed-in user to another site (open redirect). The `org-dashboard-nextjs`, `cloudflare-fullstack-nextjs` and `multitenant-saas-nextjs` blueprints each generate `src/lib/safe-redirect.ts` from the `auth/safe-redirect` partial (`safeRedirectPath(value, fallback = '/')`: a single leading `/`, not `//` or `/\`, same origin once parsed, the normalized path (`/.//host` becomes `//host`) not starting with `//`, else the fallback, which is also returned for a value the URL parser rejects (`/` followed by a tab then `/`) instead of throwing), and their forms navigate to `const destination = safeRedirectPath(...)`. `tests/integration/blueprint-safe-redirect.test.ts` evaluates the generated helper and checks every form. The `org-dashboard-tanstack-start` login route (`src/routes/_auth/login.tsx`) applies the same helper in `validateSearch`, so the form only ever navigates (`router.history.push`) to the validated `destination`; TanStack Router rewrites a search value that `validateSearch` changed before the layouts run, so a hostile `redirectTo` first lands on the cleaned `/login` URL. A new form that follows a user-supplied destination uses the same file.

The Next.js guards of `org-dashboard-nextjs` and `cloudflare-fullstack-nextjs` (`requireSession` in the `auth/session-guards` partial) send an anonymous visit to `/login?redirectTo=<requested path and query>`, which the login form passes through `safeRedirectPath`, as the Start guard does with `location.href`. A server component cannot read its own URL, so those two blueprints ship their own `src/proxy.ts` (`middleware.ts` under `cloudflare`, the same `deploymentPath` as the stack file for the cloudflare one; `org-dashboard-nextjs` cannot be deployed to `cloudflare`: postgres is a binding there and better-auth needs a module-singleton database). The stack `proxy.ts` and both blueprint files render the one `nextjs/proxy` partial, so the evlog section, the posthog matcher exclusion and the `cloudflare` naming come from one place; the blueprints pass `forwardRequestPath=true`, which copies the path into the request header named by `REQUEST_PATH_HEADER`, exported once from `src/lib/auth/request-path.ts` (the `auth/request-path` partial, generated by these two blueprints only, imported by the proxy and by the guard); under `evlog` the proxy hands `withEvlog` a `NextRequest` carrying that header. A plain better-auth project has neither the header code nor the module. The proxy replaces a client-sent value on the paths its matcher covers and the matcher skips others, so `redirectToLogin` also runs the value through `safeRedirectPath`. `tests/integration/dashboard-shell.test.ts` runs the generated proxy and guard together, and `tests/unit/templates/nextjs-proxy-partial.test.ts` renders the three proxies with evlog and posthog. `multitenant-saas-nextjs` has its own proxy that redirects with `?redirect=`; `org-dashboard-nextjs` cannot be deployed to `cloudflare` (postgres is a binding there and better-auth needs a module-singleton database), so only the cloudflare blueprint meets the `middleware.ts` name.

### Paginated lists in the org dashboards

`contact.list` and `user.list` of `org-dashboard-nextjs` (inherited by `org-dashboard-tanstack-start`) return the rows of one page by offset, with the URL as the source of truth (`?page=2&pageSize=25`), never the whole table; `contact.count` and `user.count` return the total. The page prefetches and dehydrates one page, and the back and forward buttons walk the pages.
- `packages/api/src/pagination.ts` owns the rules and is framework free: `PAGE_SIZES` (10, 25, 50, 100), `DEFAULT_PAGE`, `DEFAULT_PAGE_SIZE`, `MAX_PAGE` (10,000), `pageInput` (the `.input` of a list procedure), `parsePageParams(search)` (the same shape from a query string, which gives text, or a router, which gives numbers), `pageSearch(search)` (the page as a URL carries it: only what differs from the defaults; it is also the `validateSearch` of a Start route), `pageOffset`, `pageCountOf` and `pageControls(params, write)` (the page and its `setPage`/`setPageSize`, which hand `write` the search to put in the URL; a new page size goes back to page 1). A missing or invalid `page` (not a whole number in 1 to `MAX_PAGE`; offset pagination slows down with depth) or `pageSize` (not in the set) is the default, through `.catch`, so a hostile URL never reads an unbounded page or fails the request. A repeated parameter reads its first value, so the server (`searchParams`) and the browser (`getAll`) parse one value and the dehydrated query key equals the client's. The file is exported as `@repo/api/pagination` by the `api` entry of `ORG_DASHBOARD_PKG_PACKAGE_JSON`, so a client component never imports the router entry. `PAGE_KEYS` names its URL parameters, `parseParams(schema, search)` reads any zod object of parameters the way `parsePageParams` does, `COUNT_STALE_TIME` is the one time the tables keep a total, and `queryStringWith(current, owned, search)` writes a list back into a query string (the `owned` parameters are replaced by `search`, every other one stays), for the Next.js hooks.
- `packages/api/src/page-query.ts` is the server-only half (it imports `@repo/db`): `orderedPage(query, order, params)` applies an order, `limit` and `offset`, and `newestFirstPage(query, table, params)` orders by `createdAt` then `id`, both descending, so the order and its tie-break live once for both routers. The total is a separate `count` procedure keyed without the page, so changing page never counts again; the tables give it a `staleTime` and every mutation that adds or removes a row invalidates `count` with `list`. The `users` and `contacts` tables carry an index on `(created_at, id)` (the Drizzle schema of the blueprint, both dialects), which serves that order and its offset.
- Next.js pages read `searchParams` and prefetch `list.queryOptions(parsePageParams(await searchParams))` and `count.queryOptions()`. The Start routes set `validateSearch: pageSearch`, `loaderDeps: parsePageParams(search)` and prefetch both in a loader that still does not await. `usePageParams()` (`src/hooks/use-page-params.ts`, one file per framework because they use different routers: `.nextjs` in `org-dashboard-nextjs`, the plain one in the Start blueprint) is `pageControls` with the framework's `write`. On Next.js it is `useListParams(keys, parse, controls)` of the same file, which reads the keys of a list from the URL and hands `controls` a `write(search, mode)` (`push` unless told to `replace`), so a list with more parameters calls it with its own keys, parser and controls. A mutation that adds or removes a row calls `invalidatePagedList(queryClient, trpc.<router>)` (`src/lib/invalidate-paged-list.ts`) so the list and its `count` are fetched again together.
- The files `cloudflare-fullstack-nextjs` renders identically are partials in `partials/pagination/`: `pagination` (`pagination.ts`), `page-query` (`page-query.ts`), `table-pagination` (`table-pagination.tsx`), `use-page-params-nextjs` (the Next.js `usePageParams` and `useListParams`) and `invalidate-paged-list` (`invalidatePagedList`). Both blueprints call them, so a fix to the page rules, the pager or the URL writer is made once.
- `src/components/table-pagination.tsx` (one file for both frameworks, `'use client'` only on Next.js through `stackName`) exports `PagedList`: the one shape of a paged table (no row at all, a page past the end with a button to the last page, or the rows with the pager). The pager has the range and total in a live region, a labelled page size `Select`, and previous and next buttons that are 44px tall on a phone; a pressed button that becomes disabled hands its focus to the other. The `contact-table` and `user-table` partials render rows inside it.
- `tests/integration/blueprint-org-dashboard-pagination.test.ts` runs the generated routers and the real `usePageParams` of each stack (against a fake `next/navigation` and TanStack Router) on the real tRPC and zod; the table controls are rendered in `blueprint-org-dashboard-accessibility.test.ts`; `tests/e2e/blueprint-org-dashboard-tanstack-start.test.ts` and `tests/e2e/blueprint-org-dashboard-nextjs.test.ts` page real rows of the seeded database.

### Paginated lists in cloudflare-fullstack-nextjs

`users.list` and `documents.list` (D1, queried through `ctx.db` per request) follow the page rules above, with `count` procedures cached apart from the page (`users.count` keyed by the search, `documents.count` by nothing: the router reads the role of the caller). The users table also searches and sorts on the server, and the URL carries all of it: `?page=2&pageSize=25&search=ada&sort=-name`, each left out at its default.
- `packages/api/src/user-list.ts` (exported as `@repo/api/user-list`) extends the page with `search` and `sort` on the zod object of the shared module (`pageParams.extend`): `USER_SORTS` (`-createdAt` default, `name`, `-name`, `email`, `-email`; a leading `-` is descending) is the only way a URL picks a column, an invalid sort is the default, and a search is capped at `MAX_SEARCH_LENGTH` and kept as typed (the box that shows it must not lose a trailing space; the router ignores surrounding blanks). `userListSearch` leaves defaults out, `userListControls` is `setPage`, `setPageSize`, `setSearch` and `setSort` over a `write(search, mode)`: a new page size, search or sort goes back to page 1, and a search replaces the history entry (`mode` is `replace`) so typing never fills the back button. `useUserListParams` is `useListParams` with these keys, parser and controls.
- `usersRouter` maps each entry of `USER_SORTS` to an order in `ORDER_BY_SORT`, a `Record` over the sorts, so a sort without an order fails `tsc`, and applies it with `orderedPage`. The search is `instr(lower(column), lower(text)) > 0` over the name, the email and the role: the text is plain text (`%` and `_` match themselves, which LIKE would read as wildcards). It cannot use an index and scans the users table; the sort orders read an index and sort nothing.
- The Drizzle schema declares the indexes of the orders offered: `users (created_at, id)`, `users (name, id)` (the email is unique, which serves both email orders), `documents (created_at, id)` for an admin or manager and `documents (user_id, created_at, id)` for the documents of one user. Each order ends with a unique column, so a page boundary never repeats a row. A new sort adds its order and its index.
- `UserTable` is `DataTableShell` in server mode: `pageCount`, `state.sorting` and `onSortingChange` map the sort of the URL to the sorting of the table and back (`sortingOf`, `sortOf`; a column the list cannot order by is the default order), the `SearchInput` sits in `toolbarStart` with `hideToolbarSearch`, and a "Clear sort" button goes back to the default order (the column menu offers ascending and descending only). `renderBody` replaces the shell's table and pager with `PagedList` around the table, so the search box stays when a search matches nothing. The documents list renders its rows in `PagedList` too. The documents page has its own `h1` (the profile layout carries the one of the profile pages), a file field that is the `Input` of `@repo/ui`, a size from `formatFileSize` (`src/lib/format-file-size.ts`: bytes under 1 KB, so a small file never reads `0.0 KB`), and a delete that opens `ConfirmDialog` (`tests/integration/blueprint-cloudflare-fullstack-documents.test.ts`).
- `tests/integration/blueprint-cloudflare-fullstack-nextjs-pagination.test.ts` runs the generated routers on the real tRPC, zod, Drizzle and a real SQLite database (`bun:sqlite`, with the indexes of the generated schema): every sort, the search, the count, invalid inputs, and `EXPLAIN QUERY PLAN` of each order (an index, no temporary sort). It also runs the two URL hooks against a fake `next/navigation`. `blueprint-cloudflare-fullstack-nextjs-ssr.test.ts` checks that each page prefetches the keys its client reads and what the table writes. ### Changing the port of an app

An app's port is `3000` plus its index (`appPort`, `appUrl`, `{{port}}`). No template or META script writes one of them out: `tests/unit/no-hardcoded-port.test.ts` fails on a `3000` to `3009` in any `.hbs` or in `__meta__.ts`, so a new template takes `{{appPort appName}}` or `{{appUrl "<app>"}}` (a blueprint file of a workspace package, which has no `appName`, names its app). The `multitenant-saas-nextjs` invitation links come from one `invitationLink` in `packages/auth/src/invitation-link.ts`, which falls back to the same origin as the `getAppUrl` of the web app (`tests/integration/port-override.test.ts` compares them).
- `PORT` overrides the port of every app that listens on one, for `dev` and `start`, from the app directory and from the root. A single repo drops the `--port` flag (`PORT_FLAG` in `utils.ts`), so Next.js, Bun and `src/server.ts` take `PORT` themselves; the TanStack Start `vite.config.ts` reads it (`Number(process.env.PORT ?? <port>)`, Vite ignores `PORT`) and `.env.start` holds the app port for `start`, where a variable of the environment wins over the file. A turborepo keeps the flag as `--port ${PORT:-<port>}` (`processScriptPorts`), and the Wrangler dev script of a Hono Worker expands `PORT` itself.
- `turbo.json.hbs` lists `PORT` in `passThroughEnv` of `dev` and `start`: strict env mode drops every other shell variable. The variable reaches every app of the run, so `PORT=4000 npm run dev` at the root gives all of them port 4000 and the second one fails with `EADDRINUSE`. To move one app, run it from its directory (`cd apps/web && PORT=4000 npm run dev`); `--filter` is not documented because its form differs per package manager.
- The `ports/override` partial says so in the README and `AGENTS.md` of both repo types (and in the README of the blueprints that share `readme/getting-started`). It gates itself on `listeningApps`, so a project whose apps do not listen on a port gets nothing. In a turborepo the command that moves one app sits on its line of the app list, from the inline partial `ports/app-command` (`PORTLESS_APP_PORT=4000` under `portless`, which sets `PORT` itself, otherwise `PORT=4000`), and the override partial follows the list. Under `portless` it adds that portless assigns the port itself and ignores `PORT` (`PORTLESS_APP_PORT` pins it).
- A variable marked `origin` in META (`BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL`) is the origin the app is served from, not a port the server follows. The authentication check of a production server compares the origin of a request with `BETTER_AUTH_URL` and refuses another (`INVALID_ORIGIN`; the `allowedHosts` of the factory trust `localhost:*` only in `development` or when `BETTER_AUTH_URL` is unset, and otherwise the host of `BETTER_AUTH_URL`; trusting `localhost:*` in a production build would widen a real deploy too), and the server calls its own app through `NEXT_PUBLIC_APP_URL`, frozen at build (nothing checks requests against it). The `ports/override` partial therefore lists them per `.env` through `appOriginEnvs` (when an app defines `start` or `preview`, gated by `hasAppScript`: a `cloudflare` project has no `start`) and tells to set them to the new origin and build again before `start` or `preview`; under `portless` it adds that plain `start` does not go through portless, so the variables (which hold the portless URL) must be `http://localhost:<port>` for it, or `start:portless` is run. It renders nothing when no app has such a variable, and no template writes a variable name (`tests/integration/port-override.test.ts`). The preview of a Worker needs none of this: it serves on the port of the app (see Cloudflare).

### Cloudflare

- Every app on `cloudflare` (Next.js, TanStack Start, Hono) has one script `cf-typegen` (`wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`, the `CLOUDFLARE_TYPEGEN` constant in META) and a `postinstall` running the same command, so `tsc` and `next build` pass on a fresh install without a manual step (`cloudflare-env.d.ts` is gitignored). `wrangler` is a devDependency, so a production install (`--omit=dev`, `--production`, `--prod`) must pass `--ignore-scripts` or the `postinstall` fails; the `cloudflare/production-install` partial says so in the generated README and agent notes. A turborepo root runs it in every app with `turbo cf-typegen` (`APP_SCRIPTS_RUN_BY_TURBO`, a `cf-typegen` task in `turbo.json`), and the generated README names it through the `readme/cloudflare-types` partial. `cloudflare-static` keeps the script without the `postinstall`: nothing in a static app reads the generated types. Do not add a second name for the script.
- `cloudflare` (Workers) supports Hono (Wrangler), Next.js (OpenNext) and TanStack Start (`@cloudflare/vite-plugin`, no Nitro). `cloudflare-static` supports Next.js and TanStack Start. The deployments are `cloudflare`, `cloudflare-static`, `sst` and `terraform-aws`; the stacks each one supports are in META.
- A TanStack Start app drops `nitro` and the Nitro `start` script through `$when({ deployment: { not: 'cloudflare' } })`. `vite.config.ts.hbs` swaps `nitro()` for `cloudflare()` under `has "deployment" "cloudflare"`. `__env.start.hbs` carries `deploymentSkip: [cloudflare, cloudflare-static]`.
- Every Worker of a project binds the same D1 database: `cloudflare/d1-binding` names it `{{projectName}}-db` (never after the app) with one placeholder id, the database `db:migrate` and the seed target, and the generated notes (`cloudflare/d1-provisioning`, see below) tell to paste the one `wrangler d1 create` id into each app's `wrangler.jsonc`. Every Worker's local preview persists to the directory those scripts write (`--persist-to {{workspaceRoot}}/.wrangler` for Hono and Next.js, `persistState` for Start), because a Worker left on its own `.wrangler` state queries an empty database.
- Production servers run with `NODE_ENV=production`: Nitro through `NODE_ENV` in `.env.start`, Workers through `config: { vars: { NODE_ENV } }` on the `cloudflare()` plugin (`production` for `vite build`, `development` otherwise). Only the literal `process.env.NODE_ENV` is replaced at build time, not dynamic reads or external dependencies.
- A Next.js app on `cloudflare` declares `next`, `@opennextjs/cloudflare` and `wrangler` as a set: the `next` entry of `META.project.deployment.options.cloudflare.stackPackageJson.nextjs` overrides the stack's `^16.3.0` in a single repo, in every Next.js app of a turborepo and in `cloudflare-fullstack-nextjs`, and starts where the OpenNext `next` peer range starts (`@opennextjs/cloudflare@1.20.12` peers `next >=15.5.28 <16 || >=16.4.1` and `wrangler ^4.148.0`, the latter held by `WRANGLER_VERSION`: npm refuses to install a range that can resolve outside a peer, ERESOLVE). `1.20.12` is also the first release that serves Next.js 16.4 (before it every route answered 500, opennextjs/opennextjs-cloudflare#1355). Raise them together when OpenNext raises a peer range; `tests/integration/cloudflare-opennext-peer.test.ts` holds the peer ranges and fails when the generated ranges leave them. Next.js apps under any other deployment keep the stack range; `cloudflare-static` is a static export that never loads OpenNext.
- A Next.js app (OpenNext) gets the same through the `cloudflare/node-env-var` partial (`"vars": { "NODE_ENV": "production" }`), inserted in `wrangler.jsonc.nextjs.hbs` and in the `cloudflare-fullstack-nextjs` blueprint's own copy. Without it a dependency's runtime read of `NODE_ENV` sees `development` in workerd, because the build only inlines the literal `process.env.NODE_ENV`.
- A Next.js app on `cloudflare` or `cloudflare-static` has no `start` script (`$when(RUNS_NODE_SERVER, ...)` in META): `next start` serves it from Node, where OpenNext never initialises `getCloudflareContext` (every page answers 500), and rejects `output: export`. `build:cf` then `preview` runs the production build in workerd. `next.config.ts.hbs` calls `initOpenNextCloudflareForDev` only when `NODE_ENV` is `development`, and the app-side `getEnv()` (`src/lib/env.ts.nextjs.hbs`, and the `cloudflare-fullstack-nextjs` copy) awaits `connection()` before `getCloudflareContext`, so `next build` never prerenders a page that reads a binding: each build worker would otherwise start a local workerd on the same local D1 state and fail intermittently with `SQLITE_BUSY`.
- With D1, `src/lib/server.ts.tanstack-start.hbs` builds `db` once at module scope from `cloudflare:workers` (the db package factory stays `createDb(d1)`), plus `auth = createAuth(db, tanstackStartCookies())` when better-auth is selected. With Hyperdrive, consumers call `await createDb(env.HYPERDRIVE)` per request.
- The `preview` of a Next.js app (OpenNext) and of a TanStack Start app on `cloudflare` serves on the port of the app, which `PORT` overrides, so `BETTER_AUTH_URL` (`{{appUrl}}`) is the origin of the browser: OpenNext's is `wranglerOnAppPort('opennextjs-cloudflare preview --')` in `__meta__.ts` (the `sh -c` form of the Hono `dev`, `--port=` and `"$@"`), Start's `vite preview --port=${PORT:-{{port}}}`. The `--port=` form is the one a single repo keeps (it only strips `--port {{port}}`), and an argument appended after it (`npm run preview -- --port 5000`) repeats the flag, which Wrangler rejects: give the port through `PORT`. Without it the Worker answered `INVALID_ORIGIN` on Wrangler's port (8787), as `build:cf` bundles `BETTER_AUTH_URL` and the factory trusts its host only.
- A Hono app on `cloudflare` is a Worker only. `HONO_SERVES_FROM_NODE` (`deployment: { not: 'cloudflare' }`, next to `RUNS_NODE_SERVER` in `__meta__.ts`: `cloudflare-static` has no Hono Worker, so Hono keeps its server there) wraps the stack's Node and Bun `start` and the `@hono/node-server` and `tsx` dependencies of `HONO_ON_NODE` in `$when`. The deployment's `stackPackageJson.hono` declares `dev` (`HONO_WORKER_DEV`), which merges after the stack and replaces its Node or Bun `dev`, so `c.env` holds the bindings in `dev` (a Node or Bun process has none). `src/server.ts` carries `deploymentSkip: [cloudflare]`. Wrangler reads no port variable (it has `--port` and `dev.port` only), so `dev` is `sh -c 'wrangler dev --port=${PORT:-{{port}}} --persist-to ... "$@"' sh`: the script expands `PORT` itself and defaults to the app port, and `"$@"` hands Wrangler the arguments the package manager appends (`npm run dev -- --ip 127.0.0.1`). Portless sets `PORT` and single-quotes each argument it runs (hence the inner `sh`), and its wrapper strips only `--port <value>` with a space, so the `--port=` form stays. The `.localhost` URL therefore reaches the Worker, like a Bun Hono app. `preview` keeps Wrangler's own port. The app has no `start` script, so a turborepo root `start` and its `turbo.json` task exist only when another app declares one (`hasRootScript "start"`; `cloudflare-fullstack-nextjs` therefore has none). `wrangler dev` builds the Worker with `NODE_ENV=development` (error responses carry the stack), `wrangler deploy` with `production`. Wrangler 4.151 serves `POST /cdn-cgi/local/explorer/api/local/scheduled?worker=<name>` with a JSON body `{"cron": "<expression>"}` in plain `dev`, which fires `scheduled()` (the cron Worker of `cloudflare-fullstack-nextjs` is fired that way).
- Every Hono app on `cloudflare` types `new Hono<{ Bindings: CloudflareEnv }>()` and includes `cloudflare-env.d.ts` in its tsconfig, so `tsc` needs `cf-typegen` first (as for Start). With Hyperdrive, `wrangler.jsonc.hono.hbs` declares the `HYPERDRIVE` binding (the `cloudflare/hyperdrive-binding` partial) and route handlers call `await createDb(c.env.HYPERDRIVE)` per request.
- D1 provisioning is documented once, in the `cloudflare/d1-provisioning` partial (`deploy="<section>"` adds the deploy step and names the section that lists the build and deploy commands), rendered by the `readme/d1-provisioning` partial of both READMEs (`scripts=` is the name of their Production section), by the Cloudflare fiche (`### Database: D1`) and by the `cloudflare-fullstack-nextjs` deploy notes (without the deploy step, which that blueprint orders after R2 and the secrets). The order is: create the database, paste its id in every `wrangler.jsonc`, generate the migrations and migrate locally again (`db:generate` first: the template ships no migration, so a deploy doc followed from zero has none to apply), migrate the remote database, deploy. The steps are `orderedSteps` and `step` blocks, so each step's condition is written once and the numbers follow the steps that rendered. Each migration step renders when the root scripts it prints exist (`hasRootScript`: `db:generate` with `db:migrate` for the local step, `db:migrate:remote` for the remote one), never on `project.orm`, so a blueprint that declares its own `db:migrate:remote` gets the step (`tests/unit/templates/d1-provisioning-steps.test.ts` renders the partial over each set of scripts). Without an ORM the `d1` option declares none of those scripts (see Database first run), so the steps are the database, the id and the deploy. The deploy step does not write the commands: it points to the section `productionSteps` renders, and lists first what a deploy fails without: the secrets of every app from `appSecrets` (`secrets.required`), and any other resource a `wrangler.jsonc` binds (an R2 bucket). The production URL and the first admin are not part of it (see the next two bullets). Each step is verified against Wrangler:
  - `wrangler d1 create <name> --no-update-config` (and `r2 bucket create`) skips Wrangler's interactive "add it on your behalf?" offer: with `--no-update-config` (or `--binding`) the value is set, so the prompt is never reached. Accepting the offer would add a second binding named after the database, which the code never reads. `--binding DB` would patch `wrangler.jsonc` itself but rewrites the whole file (tabs, expanded arrays), so the docs paste the id by hand.
  - Miniflare keys local D1 data by the binding's `database_id` (`preview_database_id` first): pasting the real id switches `wrangler dev`, `preview` and `db:migrate` to a new, empty file, so the local migration (and seed) are run again.
  - `d1 create` is a binary call, not a script, so it runs from a directory that declares `wrangler`: the root in a single repo, the app `deployAppDir` names in a turborepo (the one the migrate scripts point at; a turborepo root links no `wrangler` under bun and pnpm). `db:migrate:remote` is a script: the D1 database declares it in `interactiveScripts` because Wrangler asks for a confirmation, and a database's `interactiveScripts` are exposed on the turborepo root as `cd packages/db && <pm> run db:migrate:remote` (see Database first run), so the docs print `<pm> run db:migrate:remote` for both repo types.
- The production URL is learned before the first build, by the `cloudflare/production-url` partial. The partial holds its own gate, `better-auth` (its `BETTER_AUTH_URL` is the secret that is the Worker's own URL) or `trpc` on a Next.js app (`getAppUrl()` reads `NEXT_PUBLIC_APP_URL`), and renders nothing otherwise, so every caller includes it unconditionally. `production-url` only decides the gate and what reads `NEXT_PUBLIC_APP_URL` (`publicUse`: the tRPC clause or the caller's phrase), once, and renders `production-url-section`, which holds the text. A caller whose app reads `NEXT_PUBLIC_APP_URL` through neither passes `appUrlUse="..."` (what the app does with it: a phrase that follows "which Next.js freezes into the build and"; any non-empty value opens the gate) and replaces the tRPC clause: the `cloudflare-static-site-nextjs` deploy notes pass what its sitemap, `robots.txt`, canonical URLs and JSON-LD do with it, and its `deploy` step follows the section's `export NEXT_PUBLIC_APP_URL=<the URL>`, so the `.env` copy keeps `localhost` for development. Callers: the Cloudflare fiche (`### Production URL`), both READMEs through `readme/d1-provisioning` (the D1 deploy step carries a one-line pointer, `pointer=true`, before "run the build and deploy commands", and the section follows the D1 steps) and the `cloudflare-fullstack-nextjs` deploy notes. The section starts with its own blank line, so a caller adds none and an empty render leaves the spacing alone. `wrangler deploy` is the first command that prints `https://<worker name>.<subdomain>.workers.dev`, and Wrangler has no command for the account's `workers.dev` subdomain (`whoami` prints the account id only; the subdomain is only fetched internally by `deploy`). The partial therefore reads the Workers API, `GET /accounts/<id>/workers/subdomain`, with the token of `wrangler auth token` (a Wrangler login or `CLOUDFLARE_API_TOKEN`; the command exists since Wrangler 4.148, the `WRANGLER_HIDE_BANNER=true` prefix keeps its banner, which goes to stdout, out of the token). The token goes through a pipe, `<auth token> | sed 's/^/Authorization: Bearer /' | curl -s -H @- <url>` (the inline partial `cloudflare/api-token-header` holds the first two stages, used by the `GET` and the `PUT`), never into curl's argv where `ps` shows it. Error code `10007` means the account has no subdomain yet (Wrangler offers one on its first deploy, but the URL is needed before it); the notes point to `https://dash.cloudflare.com/<account id>/workers/onboarding`, the link Wrangler itself prints, and give the API route that registers one through the same token pipe, `PUT /accounts/<id>/workers/subdomain` with `{"subdomain":"<name>"}` (`curl -s -X PUT -H @- -H 'Content-Type: application/json' -d ...`; the answer holds the registered subdomain). The worker names come from `worker-name` per app that reads the URL: an app with a secret, or a Next.js app (`projectName=@root.projectName` inside the `each`, where the context is the app); any other Worker (the cron Worker, a Hono API) is not listed. A Next.js app's `NEXT_PUBLIC_APP_URL` is frozen at build and read by the server-side tRPC client (`getAppUrl()`), so a deploy build exports it in the shell (`export NEXT_PUBLIC_APP_URL=...`, never an env prefix on a `cd apps/web && ...` subshell, which would not reach the build): a process variable wins over `.env`, so nothing needs a production value in `.env`, and the fullstack notes write `BETTER_AUTH_URL` of the first deploy's secrets file from the same variable (`printf ... > apps/web/.prod.env`) and delete the file once the Worker holds the secrets.
- The first deploy of a turborepo of Workers is the `cloudflare/first-deploy` partial, as numbered steps (`orderedSteps`): the production URL exported for the build, each secret of `deploySecrets` given a value in the shell (`export NAME=$(command)` when it has a `generateCommand`, so the developer keeps the value, which `BACKUP_TRIGGER_TOKEN` of the Payload blueprint needs later; `export NAME=` and a sentence telling to fill it when it has neither a command nor an origin, so it is never deployed empty without the reader being told), then for each app its secrets written to a gitignored `.prod.env` (an `origin` secret takes the exported URL), `build:cf` for a Next.js app, `deploy` with `--secrets-file .prod.env` when the app has secrets, and the deletion of the file. The flag goes through `runScript` with its argument: npm swallows a flag that follows the script name unless a `--` precedes it, bun forwards it either way, and pnpm 10 passes the `--` to the script itself, where a CLI ends its option parsing at it; the OpenNext CLI drops a `--` and `wrangler deploy` does not, so only the form `runScript` prints is right for every script (`tests/integration/first-deploy-commands.test.ts` runs the documented command of both blueprints over a `deploy` script that prints its arguments, under each package manager). The `cloudflare-fullstack-nextjs` deploy notes and the `cloudflare-payload-nextjs` README render it.
- The first admin of a deployed `cloudflare-fullstack-nextjs` is promoted by hand: sign-up is open and gives every account the `user` role (`defaultRole`), the seed writes the local database only and its admin has a demo password, so no seed target or bootstrap exists. The `cloudflare/first-admin` partial, rendered by the `First admin` section of `cloudflare-deploy.md` and by the README (`readme/d1-provisioning`, for that blueprint only: `docs/agents/` is not generated under `--no-agent-context`, so the README carries the steps itself and links the deploy notes only when they exist), signs up, then runs `wrangler d1 execute DB --remote --command "UPDATE users SET role = 'admin' WHERE email = lower('<your email>')"` from `apps/web` (Better Auth stores emails in lower case) (the binding `DB`, not the database name; Wrangler takes yes without a terminal). The session reads the role from the database on each request (no cookie cache), so a signed-in account sees `/admin` after a reload. `tests/integration/cloudflare-production-url.test.ts` checks the table and columns against the generated schema, and `tests/e2e/blueprint-seed.test.ts` runs the documented command, aimed at the local database, against the seeded manager account.
- R2 is not enabled on a new Cloudflare account: `wrangler r2 bucket create` fails with error `10042` (`Please enable R2 through the Cloudflare Dashboard`) and a deploy whose `wrangler.jsonc` binds a bucket that does not exist fails with `10085`. The `cloudflare-fullstack-nextjs` deploy notes (`cloudflare-deploy.md`, section R2) say to enable R2 at `https://dash.cloudflare.com/<account id>/r2/overview` and run the command again, before the first deploy. The command and that explanation are the `cloudflare/r2-bucket` partial (`suffix=` names a bucket other than `<project>-storage`, `<project>-<suffix>`), and the command alone is `cloudflare/r2-bucket-command`, which the Payload blueprint renders for its backups bucket; the fullstack deploy notes and the Payload blueprint render the same partials, so they cannot drift.
- The OpenNext warnings that change nothing (`Missing required secrets` printed at the start of `opennextjs-cloudflare deploy` by the local Wrangler session that reads `.dev.vars`, `.env` and the environment but never `--secrets-file`; Next.js's `middleware` deprecation during `next dev` and `next build`, kept because OpenNext supports the Edge runtime only; Node's `DEP0190` at the end of `deploy`) live once in the `cloudflare/opennext-warnings` partial, rendered by the Next.js section of the Cloudflare fiche and by the fullstack deploy notes. The `middleware` warning is listed only when the project generates `src/middleware.ts` (`hasAppFile`): a blueprint with no request hook has nothing to keep.
- Every Worker `wrangler.jsonc` template (every `cloudflare` and `cloudflare-static` one, and the `cloudflare-fullstack-nextjs` copies, the cron Worker included) sets `workers_dev` to `true` and `preview_urls` to `false` through the `cloudflare/public-urls` partial: Wrangler warns on every deploy that both default to enabled when the file sets neither, the Worker is served from its `workers.dev` URL (the Production URL notes depend on it), and a per-version preview URL would expose a Worker that is bound to the production database and holds its secrets.
- A Next.js Worker on `cloudflare` sets `keep_names: false` (the `cloudflare/keep-names-off` partial, in `wrangler.jsonc.nextjs.hbs` and the `cloudflare-fullstack-nextjs` copy). Wrangler bundles the OpenNext worker with esbuild's keep-names, which wraps every named function in `__name(fn, "fn")`; next-themes serializes a function with `toString()` into an inline `<script>` that runs in the browser, where `__name` does not exist, so with keep-names every production page would throw `__name is not defined` and the theme would flash before hydration (`next dev` does not go through Wrangler, so dev is not affected). Without keep-names `.name` of a function can differ from its source name after bundling, which no generated code reads. `tests/integration/cloudflare-worker-config.test.ts` checks the generated files.
- Every Worker `wrangler.jsonc` template (the Next.js, TanStack Start and Hono ones of `cloudflare`, and the `cloudflare-fullstack-nextjs` copies) ends with `{{> cloudflare/secrets-required}}`, which renders `"secrets": { "required": [...] }` from `appSecrets`, and nothing when the app has no secret. Wrangler then fails a deploy until each secret is set (`wrangler secret put`, or `--secrets-file` on the first deploy of a Worker that does not exist yet), warns in a local run (`wrangler dev`, `vite preview`) about a missing one, types each as `string` in `cloudflare-env.d.ts` (deterministic, no `.env` needed) and keeps only those keys in `dist/server/.dev.vars`. The field is not inherited by a named Wrangler environment. `cloudflare-static` has no runtime secret, so its templates carry none.
- Next.js on Cloudflare keeps its runtime secrets in `.env`, never in a `.dev.vars`. `build:cf` bundles every `.env*` value (all modes) into `.open-next/cloudflare/next-env.mjs` as a `process.env` fallback, with no opt-out: a secret set with `wrangler secret put` wins at runtime, but the bundled value is used silently when it was never set. A Worker for deploy is therefore built where `.env` holds no real secret (CI), and `preview` needs a `build:cf` after each `.env` change. OpenNext turns off Wrangler's own `.env` loading, so `preview` warns about a missing required secret even when `.env` holds it. The generated notes (`project/deployment/cloudflare/__agent.md.hbs`, the `cloudflare-fullstack-nextjs` `cloudflare-deploy.md`) say so. The CLI never writes a `generateCommand` value into a `.env` (the user pastes it), so a value bundled into a Worker is one the user set and was told about.
- On TanStack Start, `vite build` writes `dist/server/.dev.vars`, a local copy of `.env` for `vite preview` (the `secrets.required` keys only when listed). `wrangler deploy` does not upload it; `dist` ships only through `wrangler deploy`.

### Payload CMS on Cloudflare

`cloudflare-payload-nextjs` is a turborepo of `web` (Next.js through OpenNext: the Payload admin at `/admin`, its REST API at `/api` and a public site) and `cron` (Hono: the daily backup), on `database: 'd1'` without an ORM and `deployment: 'cloudflare'`. Payload 3.x supports Next.js only (TanStack Start exists in Payload 4.0 beta, with no Workers path), so there is no Start variant.
- **One version.** `payload` and every `@payloadcms/*` package are pinned to `PAYLOAD_VERSION` in `__meta__.ts` (`PAYLOAD_PACKAGES` is the list), because Payload publishes them together and each adapter peers on the exact core version. Payload 3.90.0 and later hash passwords with 600,000 PBKDF2 iterations, and Cloudflare's runtime refuses more than 100,000 (payloadcms/payload#18274): the blueprint is released once a Payload version fixes it. The cap is in the limit enforcer of Cloudflare's own runtime: open-source `workerd` (and so Miniflare, `wrangler dev` and `opennextjs-cloudflare preview`) overrides `checkPbkdfIterations()` to accept any count (cloudflare/workerd#7550), so `tests/e2e/blueprint-cloudflare-payload-nextjs.test.ts` signs in locally with the pinned version and cannot tell the edge's answer: only a deployed Worker can, and it is the release check.
- **Payload owns the schema.** The adapter has `push: false`: the schema only changes through committed migrations and their `.json` snapshots (`apps/web/src/migrations/`; a second one creates the `revalidations` table of the OpenNext D1 tag cache, whose columns the e2e compares with the installed `@opennextjs/cloudflare`, and its `preview` and `deploy` create the table when it is missing; a third indexes `publishedAt`, which the list of posts sorts by; the e2e runs `migrate:create --skip-empty` and fails when the collections need another one, so nothing in the schema may depend on the project name: the `siteName` default is a function, because a static default is written into the column and the snapshots and would fit one project name only). `payload-types.ts`, `importMap.js` and the migrations are generated and committed, and are `generatedFiles` of the blueprint. The `d1` option without an ORM emits no Drizzle script, and the root forwards `migrate`, `migrate:create`, `generate:types`, `generate:importmap`, `ensure-admin`, `db:seed` and the two `:remote` commands to `apps/web`.
- **Bindings, local first.** `payload.config.ts` reads `getCloudflareContext` in the Worker and Wrangler's `getPlatformProxy` in every Node process (the Payload CLI, `next build`, `next dev`), over the shared `.wrangler/v3`. It reaches the account only when `WRANGLER_REMOTE_BINDINGS=true` and the Wrangler config marks a binding `"remote": true`; the committed `wrangler.jsonc` marks none, because `next build` loads the config at module scope. `scripts/remote.ts` (`db:migrate:remote`, `ensure-admin:remote`) writes `.wrangler/remote-bindings.jsonc` with `DB` and `STORAGE` remote, read through Wrangler's own `experimental_readRawConfig`, runs one Payload command and deletes it.
- **Two root layouts.** Payload's `(payload)` group renders its own `<html>`, so the blueprint has no `src/app/layout.tsx`: the stack's `layout.tsx`, `not-found.tsx`, `error.tsx` and `proxy.ts` list the blueprint in `blueprintSkip`. `tests/integration/nextjs-fonts.test.ts` and `nextjs-404-landmark.test.ts` read the root layouts of an app with `rootLayoutsOf` (`tests/integration/helpers.ts`): `src/app/layout.tsx`, else the layout of each top-level route group, without the groups whose layout a library provides (`LIBRARY_ROOT_LAYOUT_GROUPS`, data). `robots.ts` and `sitemap.ts` sit in `src/app/`: `next build` 16.4 did not register `robots.ts` when it was inside the `(frontend)` group.
- **Cache.** Pages and posts are rendered on first request and kept in the R2 incremental cache (`incremental-cache/` prefix, away from the media at the bucket root) until a hook expires their tags (`revalidateTag(tag, { expire: 0 })`): `[slug]` and `posts/[slug]` export `generateStaticParams` returning `[]` and `revalidate = false`; `/`, `/posts` and `sitemap.xml` are `force-dynamic` with tagged `unstable_cache` reads, because built ahead they would query D1 before `migrate` ran. The static assets are not read first, because an entry from the build would shadow a revalidated one; the queue is the dummy one (on-demand revalidation only), so no `WORKER_SELF_REFERENCE` binding. A slug with no document answers 404 after `rememberMissing`, which gives the cached 404 the tag of the document it waits for. `revalidateTags` ignores one error, the plain `Error` Next.js throws outside a request (it has no code).
- **Media without `sharp`.** `images.unoptimized` (the OpenNext optimizer reads `ASSETS`, not R2), `crop: false` and `focalPoint: false` on `media` with `focalX`/`focalY` fields read as `object-position`, one `MAX_UPLOAD_BYTES` shared by `upload.limits.fileSize` (with `abortOnLimit`) and a `beforeChange` hook for the Local API, which skips the multipart parser.
- **First admin and seed.** `ensure-admin` creates the admin from `ADMIN_EMAIL` and `ADMIN_PASSWORD` of `apps/web/.env.admin` (a dedicated `file` variable: OpenNext bundles every other `.env*`) when `users` is empty, and the remote form refuses a password shorter than 12 characters. `db:seed` adds the sample content that is missing and deletes nothing (`seed.deletes: 'never'`). Both run through `payload run`, which loads `.env` with `@next/env` and not `.env.admin`, so the script loads that itself.
- **D1 limits** the docs state once, in `docs/agents/payload.md`: no transactions, 100 bound parameters, array fields kept small, admin preferences saved by an `onInit` patch of `upsert` (`@payloadcms/db-d1-sqlite` leaves `upsert: updateOne`).
- `tests/integration/blueprint-cloudflare-payload-nextjs.test.ts` checks the generated files and configs, `blueprint-cloudflare-payload-nextjs-logic.test.ts` runs the generated hooks, the backup and the remote config over stand-ins, and the e2e serves the production build in workerd.

### Privy and viem

`dapp-privy-nextjs` declares `@privy-io/react-auth`, `@privy-io/wagmi` and `viem` as exact versions (`PRIVY_REACT_AUTH_VERSION`, `PRIVY_WAGMI_VERSION`, `PRIVY_VIEM_VERSION` in `__meta__.ts`), never ranges. ### Third-party ids

An id or token that comes from the user's own account on a third-party service is committed blank in `.env.example`, never as a placeholder: a made-up value is truthy, so the client starts with it and fails (`[PostHog.js] Bad HTTP status: 404`, a disabled Connect button, a 403 on every page). The variable declares `thirdParty` in META (see `envs` `thirdParty`), which is the only place its name, source URL and behavior without it are written.
- The code treats blank as unset and stays quiet. PostHog initializes only when its token is set (Next.js `instrumentation-client.ts`, Start `analytics-provider.tsx`). The two dApps own their UI, so while the key id is blank `AppProviders` returns `MissingConfig` (`src/components/missing-config.tsx`, the `setup/missing-config` partial, called with the `variable` name only: its title and URL come from the `thirdPartyEnvs` entry of that variable) and mounts no Privy or wagmi provider: `wagmiConfig` of `dapp-rainbowkit-nextjs` is `undefined` without the project ID, and the Privy server client is built on the first request that carries a `privy-token` (`getPrivyClient`), never at import, so `next build` prerenders the message. A module-level `throw` for a blank third-party id would fail the first build.
- Where each id comes from, and what the app does without it, is the `env/third-party-ids` partial: a `### Third-party ids` subsection that both READMEs render after the env file lists in `## Environment Variables`, both `AGENTS.md` headers in `## Environment`, and the `showcase-nextjs` README (which has its own). It lists `thirdPartyEnvs`, has no gate of its own and holds no name, URL or blueprint check (an integration test fails on one), so it renders nothing for a project without such a variable and a new service is a `thirdParty` entry in META, never a template edit. The partial starts with its own blank line; the READMEs put each group's blank line before the group, so the partial's blank line and the one before the next heading never double.
- `tests/unit/lib/env-generator.test.ts` covers the collector, the derived comment, the blank values and one source per name; `tests/integration/third-party-ids.test.ts` checks the generated `.env.example`, README and `AGENTS.md` of PostHog projects, showcase and both dApps, and the setup message of the two dApps. ### shadcn in a turborepo

The shadcn CLI needs a `components.json` in every workspace it touches. A turborepo with `shadcn` therefore has one in each app (`components.json.hbs`, app scope) and one in `packages/ui` (`ui-components.json.hbs`, `only: mono`, `mono.path: components.json`), following the shadcn monorepo layout. Both render the fields that must stay equal (`style`, `rsc`, `tsx`, `tailwind.config`, `baseColor`, `cssVariables`, `iconLibrary`) from the `shadcn/components-config` partial, which takes the workspace's `css`; only `aliases` and `css` are written per file. The aliases agree: `ui` is `@repo/ui/components/ui`, `hooks` is `@repo/ui/hooks`, `utils` is `@repo/ui/lib/utils`, all resolved through the `exports` of `@repo/ui` (`./components/*`, `./hooks/*`, `./lib/*`, declared once by the `shadcn` library). The app points `hooks` at the package too, because the CLI writes the hooks of a component into the `hooks` alias of the app while the component imports them through the one of the package. `@repo/ui` ships `src/hooks/use-mobile.ts` so the hooks export resolves and the `sidebar` finds its hook; the file comes from the `hooks/use-mobile` partial, which the Next.js stack's `src/hooks/use-mobile.ts` renders too, so the blueprints add nothing of their own. The `tailwind.css` of an app is `../../packages/ui/src/base.css`, so the theme tokens a component adds land in the one shared stylesheet. The documented command runs from an app directory (`cd apps/<app> && <runner> shadcn@latest add <name>`, from the `shadcn` agent fiche) and installs into `packages/ui`; a single repo keeps its one `components.json` and runs the command from the root. `shadcn add` prompts before it overwrites a file the project ships (`button`, and the blueprints' components), which blocks without a terminal even with `-y`: pass `-o`. `tests/integration/shadcn-monorepo.test.ts` checks the files and aliases; `tests/e2e/shadcn-monorepo.test.ts` runs the command parsed from the generated notes of `apps/web` (`card`) and `apps/admin` (`sidebar`, with its hook) under bun, npm and pnpm (`pnpm@12` through npx when the installed one is older than 11), then type-checks and builds both apps.

The shadcn library declares only the dependencies of the components it ships (`button`, `utils`, the hooks). A blueprint that ships more declares what they import on its own `ui` package (`cloudflare-fullstack-nextjs` declares `cmdk` for its `command` component, which `data-table` imports), so a project without those components carries no `cmdk`; `tests/integration/shadcn-unused-dependencies.test.ts` fails when a workspace declares `cmdk` and no source of it imports it.

Take every version from `bundledNativeModules.json` of the `expo` package (`react` and `react-native` exact, as React Native checks the renderer version), and verify with `expo-doctor` and `expo export` on a generated project, not only `tsc`.

A single bun repo passes all 21 checks. The generated Expo `AGENTS.md` says so in a bun turborepo only (`stack/expo/__agent.md.hbs`), and the e2e fails when `expo-doctor` reports another duplicate.

## Template system

### Structure

```
apps/cli/templates/
├── stack/{stack}/                    # One directory per stack (nextjs, expo, hono, node, tanstack-start)
├── libraries/{library}/              # Per-app library templates
├── project/{category}/{option}/      # database, orm, deployment, linter, tooling options
├── blueprints/{blueprint}/           # Blueprint application code (override semantics)
├── partials/{group}/{name}.hbs       # Shared blocks inserted with {{> group/name}}, never output files
└── repo/{single,turborepo}/          # Repo-level files
```

Resolution order in `getAllTemplatesForContext`: repo, then each app's stack and libraries, then project addons (database, orm, deployment and its stack-suffixed files, linter, tooling), then the blueprint. A blueprint template replaces every structural template with the same destination. A blueprint that declares `extends` is resolved as a chain, see Template system, `extends`.

### File naming

- Template files: `filename.extension.hbs`.
- `__name.hbs` becomes `.name` (`__gitignore.hbs` is `.gitignore`); `___name.hbs` becomes `__name` (`___root.tsx.hbs` is `__root.tsx`).
- Stack-specific: `file.ext.{stack}.hbs` (`wrangler.jsonc.hono.hbs`), generated only for apps on that stack. Parsed by `parseStackSuffix` in `lib/frontmatter.ts` against the stacks in META.
- `.env.example` files and `package.json` files are generated programmatically from META, not templates.
- `__agent.md.hbs` files are agent-context fiches, not output files (see Generated agent context).

### Handlebars context

The context is `TemplateContext` (`types/ctx.ts`): `projectName`, `repo`, `apps`, `project` (`project.database`, `project.orm`, `project.deployment`, `project.linter`, `project.tooling`), `git`, `pm`, `blueprint`, `dbPort`. A file under `apps/{app}/`, and the only app of a single repo, also gets that app's `appName`, `stackName` and `libraries`. Prefer the helpers over reading these directly.

`setupTemplateEngine()` is the one engine setup: it registers the helpers and every `templates/partials/**/*.hbs` partial. Anything that renders templates (a unit test included) calls it first; `generateProjectFiles` does at the start of each generation.

### Partials

A block that several templates render identically lives once in `templates/partials/`, and each template inserts it with `{{> group/name}}`.
- **Naming**: the partial name is the file path relative to `templates/partials/`, without `.hbs`, grouped by domain: `partials/cloudflare/d1-binding.hbs` is `{{> cloudflare/d1-binding}}`.
- **Never output files**: `templates/partials/` is not a template root of the resolver.
- **Blueprint partials**: `partials/blueprints/<blueprint>/<name>.hbs` is a section that only that blueprint adds to a shared template, called with `{{> (blueprintPartial "<name>")}}` (see the helper). `readme/d1-provisioning` takes the first admin of `cloudflare-fullstack-nextjs` this way, and the AWS deploy guides take the build, live-URL and CI sections of the Lambda blueprints. `cloudflare/d1-provisioning` takes the steps a blueprint adds before and after the migration from the blueprint partials `d1-steps-before-migration` and `d1-steps-after-migration` (each a `{{#step}}` block; `cloudflare-payload-nextjs` creates its two R2 buckets before and the first admin after) and the text of its deploy step from `deploy-step` when the blueprint has one (`hasBlueprintPartial`), which replaces the generic deploy step (that blueprint points to its own first-deploy section), and `readme/d1-provisioning` the sections a blueprint puts after the generic Production URL one (the Production URL section of a blueprint whose app reads `NEXT_PUBLIC_APP_URL` through neither better-auth nor tRPC, and its first deploy) from the blueprint partial `deploy`.
- **Context**: a partial renders with the caller's context, so `has`, `hasLibrary`, `isMono` and `{{appName}}` answer as in the caller. Hash parameters add per-call values: `{{> posthog/client-options debug="import.meta.env.DEV"}}` exposes `{{debug}}` inside the partial, and a partial that takes one names it in a `{{!-- --}}` comment at its top. Partials use the template compile options, so values are not HTML-escaped.
- **Line endings**: registration normalizes the end of every partial, so an editor adding or removing a final newline changes no output.
  - By default a partial is called alone on its line (`    {{> posthog/client-options ...}}`): it replaces that line, each of its lines gets the call's indentation, and it ends with exactly one line break. Avoid blank lines inside it: they would get the indentation as trailing spaces.
  - A partial whose frontmatter sets `inline: true` is called mid-line (`'https://{{> posthog/asset-host}}/static/:path*'`): it is inserted without indentation and without a final line break. A JSON fragment appended after a property carries its own leading comma (`cloudflare/d1-binding`).
- **Shared across blueprints**: besides `org-dashboard/`, `partials/admin/generated-password.hbs` (the readonly password field with its copy button), `partials/ui/confirm-dialog.hbs` (the `ConfirmDialog` of `multitenant-saas-nextjs` and `cloudflare-fullstack-nextjs`), `partials/dates/format-date.hbs` (`formatDate`, see Dashboard shell), `partials/hooks/use-menu-confirmation.hbs` (the menu item that asks before it acts, see Dashboard shell), `partials/ui/select-field.hbs` (the shuip tanstack-form select field, rendered by `org-dashboard-nextjs`, `multitenant-saas-nextjs` and `cloudflare-fullstack-nextjs`) and `partials/navigation/breadcrumb.hbs` (the dashboard `AppBreadcrumb` component, rendered by `cloudflare-fullstack-nextjs` and both org dashboards), `partials/profile/preferences.hbs`, `partials/hooks/use-permission.hbs`, `partials/navigation/dashboard-not-found.hbs` and `partials/navigation/catch-all-not-found.hbs` (see Dashboard shell) hold a file several blueprints ship; a fix to such a file goes in the partial, never in one blueprint's copy. `partials/marketing/*` (the persona and contact pages of the two marketing blueprints, see Static export and marketing blueprints) hold the same kind of shared file. `partials/marketing/footer.hbs` (the site footer of `showcase-nextjs` and `cloudflare-static-site-nextjs`), `partials/readme/getting-started.hbs` (install, Cloudflare types, route tree, first-run steps and the `dev` step) is the Getting Started section of the single-repo README and of the `cloudflare-static-site-nextjs` and `showcase-nextjs` READMEs.
- **When to use**: a partial holds shared content (a config block, an options object, a host, an import and its call). A computed value belongs in a helper (`appPort`); whether a file exists or where it goes belongs in frontmatter or META. Choice conditionals inside a partial use the helpers like any template.

### Frontmatter

```yaml
---
path: src/lib/db/schema.ts    # Output path for single repo
mono:
  scope: app | pkg | root     # Monorepo scope (overrides META)
  name: db                    # Package name when scope is pkg
  path: schema.ts             # Monorepo path (relative to scope)
only: mono | single | no-blueprint  # Repo type or blueprint filter
deploymentPath:               # Output path override keyed by deployment platform
  cloudflare: src/middleware.ts
deploymentSkip:               # Deployment platforms that do not get this file
  - cloudflare-static
blueprintSkip:                # Blueprints that do not get this file
  - org-dashboard-nextjs
---
```

#### `deploymentPath`

A generic map of `{ <deployment platform>: <relative path> }`. When `ctx.project.deployment` matches a key, that path replaces the file's default output path (applied by `resolveDestination()` in `template-resolver.ts`, honored for every template kind). It takes precedence over `path` and `mono.path`. The replacement is the pre-scope relative path, so monorepo scoping still applies on top (`apps/{appName}/`, `packages/{name}/`, or root depending on the kind).

Why it exists: `templates/stack/nextjs/src/proxy.ts.hbs` declares `deploymentPath.cloudflare: src/middleware.ts`. Next.js 16's `proxy.ts` convention runs middleware on the Node.js runtime, which OpenNext (Cloudflare) does not support (`ERROR Node.js middleware is not currently supported`). The `middleware.ts` convention compiles to the Edge runtime that OpenNext supports. So a Next.js app deployed to Cloudflare emits `src/middleware.ts` instead of `src/proxy.ts`, and the template renders the exported function name as `middleware` versus `proxy` through `{{#if (has "deployment" "cloudflare")}}`. The file logs nothing per request. Next.js prints `The "middleware" file convention is deprecated` in every `next dev` and `next build` as long as a `middleware` file exists (an unconditional `warnOnce`, no option turns it off), so the generated agent context says why the file is named so and that it must not be migrated (`cloudflare/opennext-warnings` partial). Keep this declarative in frontmatter; do not special-case deployment, stack or filename in the resolver.

#### `deploymentSkip`

A list of deployment platforms. When `ctx.project.deployment` is in the list, the template is not generated (`isSkippedForDeployment()` in `template-resolver.ts`, every template kind). Use it when the whole file is excluded under a deployment and every other case keeps it. When the file exists only for some deployments or libraries (a shortlist, not an exclusion list), use empty-render skipping instead.

#### `blueprintSkip`

A list of blueprint names. When `ctx.blueprint` is in the list, the template is not generated (`isSkippedForBlueprint()` in `template-resolver.ts`, every template kind). Use it only when a blueprint ships its own version of a file at a different destination than the generic template it supersedes, so the override-by-destination rule cannot replace it. When both land on the same destination, the blueprint file already wins and no entry is needed. Example: the drizzle `scripts/seed.ts.hbs` lands in `packages/db/scripts/` in a turborepo, while `org-dashboard-nextjs`, `org-dashboard-tanstack-start`, `multitenant-saas-nextjs` and `cloudflare-fullstack-nextjs` keep their own root `scripts/seed.ts` there, so they list themselves (`dapp-privy-nextjs` is single-repo, its seed shares the generic destination, so it does not). The TanStack Start stack's `src/routes/index.tsx` lists `org-dashboard-tanstack-start` for the same reason: that blueprint serves `/` from `src/routes/_dashboard/index.tsx`, and two files for one route path fail the route tree.

#### `extends`

A generic field of a blueprint in META (`MetaBlueprint.extends`): the name of a parent blueprint. `resolveBlueprintChain` in `template-resolver.ts` returns the chain `[parents..., blueprint]` (grandparent first, the selected blueprint last) and `getAllTemplatesForContext` resolves each folder of the chain in that order, every one replacing the templates with the same destination that came before it, structural templates included. The child therefore gets all the templates of its parent and wins per destination, exactly as a blueprint already overrides structural templates; nothing in the resolver knows a blueprint name.
- **Templates only.** `context` (apps, libraries, database, orm, deployment), `packageJson` and its variants, `envs`, `rootPackageJson`, `pkgPackageJson`, `firstRun`, `seed` and `agentArchitecture` are read from the selected blueprint alone and are never inherited. Declare them on the child; a value both blueprints share is a constant in `__meta__.ts` that both entries use.
- **Framework-specific parent files carry the stack suffix** (`page.tsx.nextjs.hbs`), so a parent file is generated only for an app on that stack. An unsuffixed file of a parent is generated for every app of the child, so it must not import a module of one framework: `tests/unit/blueprint-extends-imports.test.ts` fails when an unsuffixed template of a blueprint that another one extends imports `next` or `next/*`.
- **`blueprintSkip` matches the selected blueprint name only** (`ctx.blueprint`), never a name of the chain. A parent file that lists the child is not generated for the child and still is for the parent; a parent file that lists only the parent is still inherited by the child. This is also how a child drops an inherited file it does not replace.
- **An invalid chain is a unit-test failure**, and throws if resolved: an unknown parent, or a cycle (including a blueprint that extends itself). `tests/unit/lib/template-resolver-extends.test.ts` resolves the chain of every blueprint in META.
- Code that scans the template folder of the selected blueprint (a test reading `templates/blueprints/{name}`) walks the chain with `resolveBlueprintChain`, not the single folder.

#### Empty-render skipping

A template whose rendered output is empty or whitespace only is not written (`processTemplate` in `template-processor.ts`, every template kind, after Handlebars rendering). Wrap the whole body in `{{#if ...}}` sections and the file does not exist when no section is active. Use it when:
- the file exists only under a choice (`{{#if (has "deployment" "cloudflare")}}`) or a combination of choices, which `deploymentSkip` (a list of deployments to exclude) cannot express;
- the file is a shared entry point that only exists when a library contributes to it (see below).

Example: `repo/turborepo/pnpm-workspace.yaml.hbs` is wrapped in `{{#if (eq pm "pnpm")}}`. pnpm ignores the `workspaces` field of `package.json`, so a pnpm turborepo needs this file while bun and npm get none. A single repo gets one only when `installScripts` has an entry (`repo/single/pnpm-workspace.yaml.hbs`). `linkWorkspacePackages: true` makes the `*` range of internal dependencies resolve to the workspace package, as under bun and npm. Its `packages` globs must match `workspaces` in `generateRootPackageJson`; an integration test checks it.

#### Shared stack entry files with library sections

A file several libraries extend (a framework entry, a global middleware list) is owned by the stack template, never by one library, so the next library adds a section instead of colliding on the same path. The stack template holds the unconditional skeleton, and each library contributes a `{{#if (hasLibrary "x")}}` section that wraps or extends it, like `stack/nextjs/src/proxy.ts.hbs`:
- `stack/tanstack-start/src/server.ts.hbs` is the Cloudflare Worker entry. It is always generated under `cloudflare` (`wrangler.jsonc` `main` points to it unconditionally) and exports Start's handler; a library section wraps `fetch` inside it (evlog: `withEvlog` + `loggerStorage.run`).
- `stack/tanstack-start/src/start.ts.hbs` is Start's `createStart` instance. The gate lives at the top of this one file, as `{{#if (or (hasLibrary "x") ...)}}` listing the libraries that contribute (a project with none gets no file). Libraries only add entries to `requestMiddleware` and `functionMiddleware`.
- A library section must never drop framework defaults. Start applies its default CSRF middleware to server functions only when `src/start.ts` does not exist, so the skeleton always declares `csrfMiddleware` (`createCsrfMiddleware({ filter: (ctx) => ctx.handlerType === 'serverFn' })`, the same call as Start's default) first in `requestMiddleware`, before any library entry. The same holds for any shared entry file whose presence disables a framework default.
- `src/routeTree.gen.ts` is committed (TanStack's convention) but only exists after the first `vite dev` or `vite build`, so a fresh install would fail `tsc` and the editor. The stack declares the `postinstall` `tsr generate` (`GENERATE_ROUTE_TREE` in META) with `@tanstack/router-cli` (a dependency, not a devDependency, so `postinstall` still finds `tsr` in an install without dev dependencies), and `stack/tanstack-start/tsr.config.json.hbs` carries the footer the Start Vite plugin appends to the file (the `Register` block, `createStart` or `startInstance` import), so the file written on install is byte-identical to the one `vite dev` and `vite build` write and committing it causes no churn. Its start-file condition mirrors the gate of `src/start.ts.hbs` (the library list and `cloudflare-static`): change both together. The later declaration of a script name overwrites the earlier one: on `cloudflare` the deployment's `stackPackageJson` for Start declares the `postinstall` as `${CLOUDFLARE_TYPEGEN} && ${GENERATE_ROUTE_TREE}`, so any new `postinstall` step is chained there, never added as a second declaration. The generated README names the file through the `readme/route-tree` partial.
- Express "this file is useless here" with `deploymentSkip` frontmatter in the file itself (both files above skip `cloudflare-static`, where nothing runs per request).

### Triple-slash directives

TypeScript honours `/// <reference ... />` only before the first statement, and a formatter that sorts imports (oxfmt) carries a leading comment with the import it precedes, so a directive in a file with several imports can end up below one. A template therefore never holds a directive and two or more imports: the types come from a declaration file with no other statement (`stack/tanstack-start/src/vite-env.d.ts.hbs` declares `vite/client`, which types `import.meta.env` and `?url` imports), or from the tsconfig `types`. The threshold of two follows oxfmt, which keeps a single import in place: `sst-env.d.ts.hbs` carries a directive and one `import "sst"`. `tests/unit/triple-slash-directives.test.ts` checks every `.hbs` under `templates/` (partials included), and `tests/integration/triple-slash-directives.test.ts` checks the sources of generated projects, which can take imports from partials.

### Scope mapping and path resolution

Scopes: `app` is `apps/{appName}/` (turborepo) or the root (single repo); `pkg` is `packages/{name}/` (turborepo only; the name comes from `mono.name` in frontmatter or META); `root` is the project root.

Each per-kind resolver in `template-resolver.ts` first drops excluded files with `isTemplateExcluded`: `only` does not match the repo type or blueprint, `ctx.project.deployment` is in `deploymentSkip`, or `ctx.blueprint` is in `blueprintSkip`. `resolveDestination()` then computes the path only:
1. Take the relative path from `deploymentPath[ctx.project.deployment]` when present (it overrides `path` and `mono.path`).
2. Single repo: `frontmatter.path`, else that relative path; the scope is not used.
3. Turborepo: scope from `frontmatter.mono.scope`, else the addon's META `mono.scope`, else the default of the template kind: `app` for stack, library, stack-suffixed addon and blueprint files; `root` for repo files and for project addon files (database, orm, deployment, linter, tooling). Then apply the scope prefix above.

### Generated `.env.example` files

Env variables are declared in META (`envs` on libraries, project addons and blueprints) and written by `lib/env-generator.ts`: `collectEnvFiles(ctx)` returns `{ destination, content }[]`, and `collectEnvGroups(ctx)` returns `{ path, vars[] }[]` for the README and agent-context rendering.
- **Value placeholders** (`resolveEnvValue`): `{{projectName}}` and `{{dbPort}}` (when the context has a database port) everywhere; `{{appPort}}` and `{{appUrl}}` for app-scoped variables (`appUrl` is `http://localhost:{port}` unless a selected tooling addon's `runtime.resolveAppUrl` provides it).
- **Who receives a variable**: a library env goes only to the apps that have the library; a project addon env goes to every app. An env with `stacks` is further limited to apps on a listed stack (see `envs` above). Blueprint envs follow the project addon rule; the `envs` of an app in the blueprint `context.apps` go to that app alone (see Blueprint apps).
- **A variable has a reader.** Every variable of a generated `.env.example` is read by code that runs with that file (its package, the workspace packages the app uses, or the script that loads it through `--env-file`), or by a dependency of the app (`BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` are read by `better-auth` itself), and every variable a generated source reads (`process.env.X`, `import.meta.env.X`, `env.X`) is declared in one of them, except what the shell or the tool provides (`NODE_ENV`, `PORT`, `PORTLESS_URL`, and the Vite built-ins of `import.meta.env`) and the Worker bindings; a read is checked against the examples of its own app or package, of the workspace packages it uses and of the apps that run it, not against the whole project. So a variable is scoped to the package that reads it: `BETTER_AUTH_SECRET` is `app` only, never `{ pkg: 'auth' }`, because nothing runs from `packages/auth`. A library that reads a variable declares it (`trpc` declares `NEXT_PUBLIC_APP_URL` for `getAppUrl()` on Next.js). `src/lib/get-app-url.ts` and the portless `env` of `next.config.ts` are generated only for an app that receives `NEXT_PUBLIC_APP_URL` (`receivesEnv`), so a plain Next.js app has no read of it. `tests/integration/app-scope.test.ts` generates every blueprint and the choices of META packed into projects and fails on a variable nothing reads or a read nothing declares for its package. A database without an ORM keeps its connection variables for the client the user brings.
- **Scope to path**: in a turborepo `{ pkg: 'db' }` is `packages/db/.env.example`, `'app'` is `apps/{appName}/.env.example`, `'root'` is `.env.example`. A `{ pkg }` scope is only written when that package is generated, by the same collector as the package manifests (`collectMonoPackages` in `package-json-generator.ts`): a database env scoped to `{ pkg: 'db' }` lands in `packages/db/.env.example` only with an ORM, and without one it stays in each app's file. A variable whose scopes are all missing packages falls back to the app scope. In a single repo every scope collapses into the root `.env.example`. Lines are deduped by variable key within each file. The Cloudflare account credentials of D1 (`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_DATABASE_ID`, `CLOUDFLARE_API_TOKEN`) are read only by `drizzle-kit` (`d1-http`, `NODE_ENV=production`), so they live in `packages/db/.env.d1.example` (a turborepo) or the root `.env.d1.example` (a single repo), never in an app's `.env.example`.

### Blueprint apps

A blueprint gives its dependencies and variables to the apps that use them. `packageJson` and `envs` of the blueprint reach every app; an app of `context.apps` (`MetaBlueprintApp`) may carry its own `packageJson` and `envs`, applied to that app alone, on top of its stack, its libraries and the blueprint's (so the app wins on a key both set). Core code reads it through `getBlueprintApp(ctx, appName)` in `addon-utils.ts`, by app name, in `composeApp` (`package-json-generator.ts`), in `collectAllEnvs` (`env-generator.ts`, which tags the variable with its app so `appAcceptsEnv` filters it: `collectAppSecrets`, `collectProjectSecrets`, `collectTaskEnv`, `collectEnvsToGenerate`, `collectThirdPartyEnvs` and the first-run env copy all follow) The generation context keeps only `appName`, `stackName` and `libraries` of each app (`getBlueprintAppContexts`), so the scoped data is never in a template context. A variable of an app with a `root` or `pkg` scope is still written once for the project. A server-only app (`type: 'server'` in `META.stacks`: Hono, Node) receives no UI dependency: the React packages, icon sets and toast libraries of a dashboard sit on its `web` app (`tests/integration/app-scope.test.ts` derives the UI dependencies from META and from the packages only JSX files import). The tests also generate every project that deploys to Cloudflare and fail when `SEED_PASSWORD` is in a `.env.example` OpenNext reads. What no Worker should bundle stays out of every `.env` it reads: the seed password of `cloudflare-fullstack-nextjs` is a `root` variable in the dedicated file `.env.seed` (`file: 'seed'`), loaded by the root `db:seed` next to `apps/web/.env`, because `build:cf` bundles every `.env*` value of `apps/web` and of the monorepo root (OpenNext reads the root of the workspace, the first parent with a lockfile) into the Worker.

### Turborepo workspace packages

A workspace package is generated from META (`collectMonoPackages`): library and ORM `packageJson`, plus the blueprint's `pkgPackageJson`, merged per package.
- **`exports`** only lists files that are generated for the combination. An export a blueprint alone satisfies (`@repo/auth/permissions`, `@repo/ui/hooks/*`) is declared in that blueprint's `pkgPackageJson`, never in the library, and one that depends on a choice uses `$when`. `tests/integration/package-exports.test.ts` generates representative combinations and every blueprint, and checks that every export target exists and every `@repo/x/y` import in the generated sources is covered by an export.
- **`tsconfig.json`** of each package lists the `types` it needs and extends `@repo/config/ts/*` (`react-library.json` has the DOM lib; `base.json` has none). A package compiles the sources of the workspace packages it depends on, so it carries their types too: `@types/node` for `process`, `@cloudflare/workers-types` under `cloudflare` for the `D1Database` and `Hyperdrive` bindings, each added as a devDependency with `$when`. `tests/integration/workspace-package-tsconfig.test.ts` checks it, and `tests/e2e/workspace-packages-typecheck.test.ts` runs `tsc --noEmit` in every app and package.

### Versions across the workspaces

A turborepo root runs syncpack 15: `versions:list` is `syncpack lint` and `versions:fix` is `syncpack fix` (the v13 `list-mismatches` no longer exists; v14 merged it into `lint`, and dropped the `dependencyTypes` and `lintFormatting` config keys). Its config is the `syncpack` key of the root `package.json`, generated by `collectSyncpackConfig` (`lib/syncpack-config.ts`), never written by hand: a version group ignoring the workspace packages (`$LOCAL`: their `*` range against the `0.0.0` of the package itself), then, for each app, a group ignoring the `pinnedPackages` of its stack and libraries with `packages: [appName]`, so the other apps still have to agree among themselves.
- Everything else has one range. `tests/unit/meta-package-ranges.test.ts` walks every `dependencies` and `devDependencies` of META and fails, naming the package and the choices, when two choices a project can hold together declare it on different ranges. Left out: the packages a stack or library pins (`pinnedPackages`), a deployment's own `stackPackageJson` (it replaces the range of the stack by design: the `next` of OpenNext), and choices a project holds only one of (the blueprints, the options of a single-selection category). A package that drifted takes one constant in `__meta__.ts` (`TYPESCRIPT_VERSION`, `REACT_TYPES_VERSION`, `VITE_VERSION`, `PG_TYPES_VERSION`). The TypeScript range is `~6.0.3`, the one `expo-doctor` expects of the Expo SDK, so every stack runs TypeScript 6 and none is on another major (TypeScript 7 has no programmatic API until 7.1 and `typescript-eslint` peers `<6.1.0`). TypeScript 6 loads no `@types` package on its own, deprecates `baseUrl` and turns `strict` on by default, so a stack `tsconfig.json` lists its `types` (`"node"` for Hono, Node and TanStack Start, as the packages and Expo do) and declares its `paths` relative to the tsconfig (`"@/*": ["./src/*"]`) without `baseUrl`. The root dev tools of a turborepo (`rimraf`, `syncpack`) are declared in `META.repo.stacks.turborepo.packageJson` next to the scripts that run them.
- `tests/integration/syncpack.test.ts` generates turborepos with and without Expo (bun, npm and pnpm), the choices of META packed into projects (`groupChoices` of `tests/choice-projects.ts`, a Node app added when a project has one app) and every blueprint with several apps, runs the real syncpack (a devDependency of `apps/cli`, kept on the major the generated root declares) and requires `lint` to pass and `fix` to leave every `package.json` byte-identical. A new library whose dependency differs from another app's must either use the shared range or declare `pinnedPackages`; the integration test names the package and the workspaces.
- syncpack 15 has no JavaScript dependency, which removed the six high-severity advisories `syncpack@13` brought through `fast-glob`, `micromatch` and `braces` into a fresh `npm install`. The highs that remain come from the choices: `braces` (advisory `<=3.0.3`, no fixed release) through `@next/eslint-plugin-next` with ESLint and through `tailwindcss` 3, `jest` and `expo` with Expo.

### Generated `.gitignore`

`.gitignore` is a template per repo type (`templates/repo/{single,turborepo}/__gitignore.hbs`), one section per choice with `has` conditionals (`{{#if (has "stack" "tanstack-start")}}`). A directory that a stack, library or deployment writes at build or dev time and that must not be committed (`.output/` and `.tanstack/` for TanStack Start, `.wrangler/` for Cloudflare) goes in that choice's section. The dedicated env files of `EnvVar.file` (`.env.d1`, `.env.seed`) are not in a section: the "Local env files" list renders them from META through `envFiles`.
Keep the two files in step.

Under `sst` the root `sst.config.ts` is not compiled by the app: `sst install` writes `.sst/platform/config.d.ts`, which imports the whole SST platform source (about 600 type errors under `verbatimModuleSyntax`), and `**/*.ts` includes `.sst/` as well. A single-repo Next.js or Expo `tsconfig.json` therefore lists `.sst` and `sst.config.ts` in `exclude` (`{{#unless (isMono)}}{{#if (has "deployment" "sst")}}`): excluding the directory alone is not enough, because an imported file is compiled whatever `exclude` says. `tsc` and `next build` then pass before and after `sst install`; SST bundles the config with esbuild and never type-checks it, and an editor gets its types from the `/// <reference path>` once `sst install` (run by `sst dev` and `sst deploy`) has written the platform. A turborepo app sits in `apps/<app>`, away from the root files, so its tsconfig is unchanged.

### Generated agent context

Every generated project gets an `AGENTS.md` plus a `CLAUDE.md` containing exactly `@AGENTS.md`, next to every `AGENTS.md` (the root one and, in a turborepo, `apps/{app}/`). `--no-agent-context` skips them and any blueprint `docs/agents/` file. `lib/agent-context-generator.ts` assembles them from `__agent.md.hbs` fiches placed beside the stack, library and project addon templates (frontmatter `scope`, `heading`, `order`; a fiche rendering empty is dropped), under the header `repo/{single,turborepo}/__agent.md.hbs`. Blueprints add an About section and the `agentArchitecture` text from META. The generator writes the `## <heading>` of each fiche, so a fiche's own headings are `###` and its body opens with text (a heading directly followed by another heading is a unit-test failure, `collectAgentContextFiles (headings)`).

A statement in a fiche is true for every combination that renders it, so a path that a repo type or a workspace package moves is written through `isMono` or `hasPackage` (the tRPC routers are in `packages/api/src/router/` when the `api` package exists, in `src/trpc/routers/` otherwise), and a path the user is told to edit is the file that holds the code (the Hono routes are in `src/app.ts`, `src/index.ts` is only the entry; Better Auth has no `socialProviders` key until one is added to the `betterAuth(...)` call). Each item of a list opens with what it describes: no "the same way" that refers to an item another combination does not render. The `## Scripts` of both `AGENTS.md` headers and the `## Available Scripts` of the turborepo README render one partial, `scripts/root-list`, which renders the `scriptList` helper: a script is listed only when the generated root `package.json` defines it, and a turborepo root script is worded as running in "every app that has" it, because an Expo app has no `dev` or `build` (the sentences are `scriptDescriptions` in META). A new root script gets its sentence in META, not a line in the partial. `tests/integration/agent-statements.test.ts` generates single repos, turborepos and blueprints and checks that every `src/`, `packages/`, `apps/`, `docs/` and `scripts/` path an `AGENTS.md` or `docs/agents` guide writes exists (the exceptions are listed in the test: env files the user copies, the Drizzle migrations directory, `src/start.ts`), that the fiches name the directory of the tRPC routers, the file that registers the Hono routes and the file that calls `betterAuth`, that the `Scripts` section is the root scripts, and that the seed messages name scripts that exist.

Every stack has a fiche, because the turborepo header promises one `apps/<app>/AGENTS.md` per app (`tests/integration/agent-statements.test.ts` fails for an app without it). Each linter and Husky has one too (`project/linter/<name>/__agent.md.hbs`, `project/tooling/husky/__agent.md.hbs`, sections `Biome`, `Oxlint + Oxfmt`, `ESLint`, `Prettier`, `Husky`, after the libraries). The generator walks `getSelectedProjectAddonEntries` (`addon-utils.ts`: the selected `{ category, name, addon }` with each composite addon expanded, the list `getSelectedProjectAddons` maps over), so a composite addon (`compose`, `eslint-prettier`) has no fiche of its own: it contributes the fiche of each addon it composes, in order, and the ESLint and Prettier sections are written once. The ESLint fiche is true for both repo types: a turborepo has no root ESLint configuration, `packages/eslint-config` holds the presets, and each app and each workspace package that holds code has its own `eslint.config.mjs`, `lint` script and `lint-staged` key (`packages/config` has none). The Husky fiche lists no task: it points to the `lint-staged` key of the root `package.json`, or in a turborepo with ESLint to the key of each workspace that lints itself, so a linter's tasks are written once, in META. The Prettier, Biome and Oxlint + Oxfmt fiches state the style, the ignored files and the script behavior of their generated files. `tests/integration/linter-tooling-fiches.test.ts` generates every linter in a single repo, a turborepo and a TanStack Start turborepo and checks each statement against the generated files and `package.json`.

The seeds delete users: the generic Drizzle and Prisma seeds, the rainbowkit one and the privy one delete every user (and the posts, where the schema has them) before they insert the sample rows, and print it first; the blueprints whose seed declares `with-reset` (`cloudflare-fullstack-nextjs`, `org-dashboard-*`, `multitenant-saas-nextjs`) delete only with `--reset`. A blueprint that ships its own seed declares what it does in META (`seed`, see META capabilities) and the documents render that data, so they cannot drift from it: `seed/blueprint` (through the `blueprintSeed` helper, with the inline `seed/rows` that lists the rows) is rendered by the `data-layer.md` of every blueprint that declares a seed, and by the README. `seed/deletes-users` is the sentence of a seed that deletes users every time: the ORM seed (ORM fiches, `unless blueprint`, the `data-layer.md` of rainbowkit, which ships none, and the README of a project whose blueprint declares none) and, through `seed/blueprint`, a blueprint seed that declares `always` (privy), so there is one sentence for both. The README has a `## Seeding` section (`readme/seeding`, gated on `hasRootScript "db:seed"` or `hasRootScript "local-setup"`, so it exists under `--no-agent-context` too and wherever a script list points to it; `tests/integration/script-list-sections.test.ts` checks every pointer) that renders `seed/blueprint` when the blueprint declares a seed and `seed/deletes-users` otherwise, then the `local-setup` sentence from META (`scriptDescription "local-setup"`); the `db:seed` and `local-setup` sentences (`SEED_DATABASE`, `SET_UP_LOCAL_DATABASE` in `__meta__.ts`) say they can delete data and declare `readmeSection: 'Seeding'`, which `scripts/root-list` renders as a pointer ("below" in the README, which passes `readme=true`; "in the README" in the `AGENTS.md` headers), and name no blueprint. A partial that opens a README section starts with its own blank line and the caller adds the one after it, so no heading sits directly under text, and a paragraph, list or table never follows a paragraph line directly (Markdown would render it inside that paragraph) nor does a blank line double (`tests/integration/agent-statements.test.ts` checks the README of every project it generates, blueprints included). A block a README ends with is not followed by a blank line of its own when a partial that starts with one comes after it (`readme/getting-started` ends on its last line). The `local-setup` of `cloudflare-fullstack-nextjs` also deletes the local D1 state, which its `firstRun` description and `data-layer.md` say. A seed message that tells to run a script names one the root `package.json` defines in both repo types (`db:generate` then `db:migrate`; `db:migrate:local` exists in a single repo only). The dev sentence of both READMEs and of the script list is the `scriptDescription "dev"` helper, from the `dev` entry of each stack.

The Next.js `next.config.ts.hbs` sets `agentRules: false` (option of Next.js 16.3 and later, hence `next: ^16.3.0`). Without it `next dev` run by a coding agent appends its own managed block to `AGENTS.md` (or creates the file under `--no-agent-context`), leaving a fresh project dirty in git. The Next.js fiche points to `node_modules/next/dist/docs/` instead.

## Conventions

### Naming
- Choice values (stacks, libraries, options) are lowercase kebab-case: `nextjs`, `tanstack-start`, `better-auth`.
- Types PascalCase (`MetaStack`, `AppContext`), functions camelCase, files lowercase kebab-case, templates `feature.extension.hbs`, special files with the `__` prefix (`__meta__.ts`).
- Package names of generated monorepo packages are defined in META (`mono.name`, for example `db`).

### Type safety and structure
- Strict TypeScript (`packages/config/ts/base.json`), no `any`.
- Types are inferred from META, which is declared `as const satisfies Meta`.
- `@/*` maps to `apps/cli/src/*`.
- Early returns, validation first, graceful cancellation, one error path in the prompt wrappers (`handlePromptCancel`).

### Tooling
- Format and lint rules are in `biome.json`, checked by `bun run check` (CI and the pre-commit lint-staged hook run Biome).
- Commit types are enforced by `.husky/commit-msg`.
- CI (`.github/workflows/ci.yml`) runs `bun run check`, `bun run check:unused`, `bun run typecheck`, `bun run build:cli`, unit and integration tests. Releases are automated by `.github/workflows/release.yml` (release-please, then `npm publish`).

## Agent-generated documentation

All documentation produced by AI agents (research reports, plans, audits, cleanup assessments) MUST be written under `docs/agents/`, organized by topic (for example `docs/agents/cleanup/`, `docs/agents/superpowers/plans/`). Never write agent-generated docs to the `docs/` root or other locations.

## Skills

`.claude/skills/` holds workflow skills for Claude Code; the rules above apply to all of them.
- `adding-templates`: add a stack, library or project addon.
- `adding-blueprints`, `extracting-blueprints`, `extracting-templates`: compose a blueprint, or extract one from a working project.
- `updating-libraries`: bump library versions in META.
- `fixing-templates`: fix indentation and spacing in `.hbs` files.
- `documenting-stack`, `documenting-module`, `documenting-blueprint`: write the MDX docs under `apps/www/content/docs`.

## Adding content

### Stack
1. Add the name to `StackName` in `types/meta.ts` and the entry to `META.stacks` in `__meta__.ts`.
2. Create `templates/stack/{stack}/` with `.hbs` files (frontmatter where needed).
3. Declare in META which libraries and deployments support it (`support.stacks`, `stackPackageJson`).
4. Describe its scripts: `scriptDescriptions` (`dev`, ...) and `productionScripts`.
5. Test with `bun run dev:cli`.

### Library or project addon
1. Add the entry to `META.libraries` (or to `META.project.{category}.options`) with `support`, `require`, `packageJson`, `stackPackageJson`, `envs` as needed, and a `scriptDescriptions` entry for each root script it declares (a unit test fails without it).
2. Create `templates/libraries/{library}/` (or `templates/project/{category}/{option}/`); put stack-specific files in `file.ext.{stack}.hbs`.
3. Test with `bun run dev:cli`.

### Blueprint
1. Add the entry to `META.blueprints`: label, hint, category, `context` (apps with their libraries, plus `database`, `orm` and `deployment`), optional `packageJson`, `envs`, `scriptDescriptions` (for a root script of its own), `agentArchitecture`, and `seed` when it ships a `scripts/seed.ts` (a unit test fails without it). A dependency or variable that only some apps use goes on that app of `context.apps`, not on the blueprint.
2. Create `templates/blueprints/{blueprint}/` with `.hbs` files; a blueprint file overrides a structural template with the same destination, `blueprintSkip` covers a different one. A framework variant of an existing blueprint sets `extends` to it and ships only the files that differ (the parent's framework-specific files carry the stack suffix); it still declares its own `context`, `packageJson`, `envs`, `firstRun` and `seed`.
3. Test with `bun run dev:cli` and the `--blueprint {name}` flag.

## CLI flags

`bunx create-faster [project-dir] [options]`; `--help` prints the current choices, the stacks each library supports included (read from META), and wraps its Prompts paragraph at the width commander wraps the options at. The positional argument is the project directory, a name or a relative or absolute path (`../out/my-app`, `./apps/my-app`): the files go to that directory resolved against the working directory, the project name (`{{projectName}}`, the package name) is its last segment, validated by `validateProjectName` (`lib/project-location.ts`: lowercase letters, digits, `-`, `_`, `.`, starting with a letter or digit; refused before anything is written, in flags and in the prompt). An app name (`--app <name:...>`, the app prompt) follows the same rule through `validateAppName`: it becomes the `apps/<name>` directory and the package name, so a space, uppercase letter, `/`, `..` or a leading `-` or `.` is refused with an `App name ...` error before anything is written (`--app` exits 1; the prompt shows the error and asks again). The recreate command therefore never quotes an app name. The context keeps the directory as typed in `projectDir`, which the `cd` step, the install-failure retry command and the printed recreate command use, so they stay valid from the same working directory; `getProjectPath` is the absolute target. A directory printed in a command goes through `quoteProjectDir` (single quotes unless it holds only safe characters, a leading `+`, `=` or `-` counting as unsafe, and a `./` prefix when it starts with `-` so it is not read as an option; `create-faster -- -x/my-app` also reads it as a directory), so a path with a space or a shell metacharacter pastes correctly. The name prompt accepts a path too. Omitted answers are prompted, per answer: a project category (database, ORM, deployment, linter, tooling) that a flag or the blueprint answered is skipped, the others are asked, and a category whose `require` is unmet is not offered. Prompts for what no flag answered are only asked in an interactive terminal (`process.stdin.isTTY` and `process.stdout.isTTY`) once any flag is passed (`arePromptsSuppressed` in `lib/project-prompts.ts`); without one, project categories stay empty, a missing `--git`/`--no-git` means no git and a missing `--pm`/`--no-install` means no install, so scripts and agents never block. `--yes` suppresses them in a terminal too (the project name and the apps are still asked). Those two answers have no default, so without a terminal a missing project name or a missing `--app`/`--blueprint` exits 1 before the banner and before anything is written, each error naming the argument or flag to pass (`missingAnswersWithoutTerminal` in `lib/project-prompts.ts`, checked right after the flags are parsed); no prompt is ever printed there. A text prompt with a `defaultValue` (project name `my-app`, app name `app-N`, app count `1`) starts empty with the default as placeholder, and `promptText` validates the default when enter is pressed on an empty value. Every prompt of the flow carries `n/total` from `Progress` (`tui/progress.ts`): each prompt registers an id when it is shown, and the total is the prompts shown plus the ones the answers so far say will still be asked (`expectedCategoryPrompts`, `isGitPrompted`, `isPackageManagerPrompted` in `lib/project-prompts.ts`, the app prompts in `cli.ts`), so a prompt that stops being expected, such as the ORM once no database is chosen, shrinks the total. The choice between a template and a custom stack and the template choice are numbered too (`promptForContext` in `cli.ts` passes them to the flow as already asked). A new prompt registers its id in the plan built by `startCustomFlow` or `startBlueprintFlow`, and a condition that decides whether a prompt is asked (`asksAppName`, `asksLibraries`, `expectedCategoryPrompts` over `isProjectCategoryAvailable`) is one predicate used by the plan and by the prompt. Tests drive the real prompts on a pseudo-terminal through `tests/pseudo-terminal.ts` (`runOnPseudoTerminal`, used by `runCliOnTerminal` in `tests/integration/helpers.ts`); `tests/integration/prompt-defaults.test.ts` runs the real name prompts and `tests/unit/cli-flow-progress.test.ts` the numbering. Spinners go through `taskSpinner` (`tui/task-spinner.ts`): when stdout is not a terminal (a file, a CI log) the start and the end of a task print as plain lines, never as frames with cursor codes. The install prompt (`promptSelectWithDisabled`) starts on its first selectable option, the first package manager that is installed, never on `Skip installation`: the function passes that option's value as `initialValue`, because clack otherwise starts on the option whose value is `undefined`, which is `Skip installation` here and the `None` option of a category prompt. `tests/integration/install-prompt.test.ts` drives it on a pseudo-terminal with stand-in package managers first on `PATH` (`runCliOnTerminal` takes the environment as a last argument). The repeatable `--app` and `--tooling` have no commander default, so `--help` prints no `(default: [])` for them. The generation step announces `Generating files...` and ends with `Generated N files successfully!`, where N is the number of files written: a template that renders empty writes nothing and is not counted (`tests/integration/non-terminal-progress.test.ts` compares N with the files on disk). A cancelled prompt (Ctrl-C, `handlePromptCancel`) exits 1. A run with no flag at all prompts everything. `require` and capability checks of what the flags selected (`validateRequirements`) run right after the flags are parsed without a terminal, and after the prompts in a terminal, so `--app web:nextjs:better-auth` prompts the database instead of failing; what a prompt leaves unmet is rejected after it. The needs of Husky are its META `require`, checked like any other. Every project category flag accepts `none` (`--database none`, `--tooling none`), validated generically from `META.project`: the category is answered with no selection, so it is neither prompted nor filled; `none` cannot be mixed with another `--tooling` value. The recreate command printed by `tui/summary.ts` is exact: it adds `--yes` when it leaves a category, git or the package manager empty (shorter than `none` per category), and `--no-install` next to `--pm` when the install was skipped. Flags are declared in `apps/cli/src/flags.ts`, which is authoritative.

| Flag | Meaning |
|---|---|
| `--app <name:stack:libraries>` | Add an app, repeatable. Libraries are comma-separated and optional: `--app web:nextjs:shadcn,mdx` |
| `--blueprint <name>` | Use a blueprint. Cannot be combined with `--app`, `--database` or `--orm`; `--deployment`, `--linter` and `--tooling` still apply |
| `--database <name>`, `--orm <name>` | Project database and ORM; an ORM requires a database |
| `--deployment <name>` | Deployment platform |
| `--linter <name>` | Linter (single selection) |
| `--tooling <name>` | Tooling, repeatable |
| `--git` / `--no-git` | Initialize a git repository or not |
| `--pm <bun\|npm\|pnpm>` | Package manager |
| `--no-install` | Skip dependency installation |
| `--no-agent-context` | Skip `AGENTS.md` and `CLAUDE.md` |
| `--yes` | Ask nothing no flag answers: project categories stay empty, no git, no install |
| `--version`, `-V` | Print the version of `apps/cli/package.json` and exit 0: no banner, no terminal and no other argument needed |
| `none` as a value | Any project category flag: explicit "no selection" |

```bash
bunx create-faster mysaas \
  --app web:nextjs:shadcn,tanstack-query \
  --app api:hono \
  --database postgres --orm drizzle \
  --linter biome --git --pm bun
```

The valid values of each flag come from META; flag validation, `require` rules and runtime-capability checks are applied generically (`validateContext`). After generation the CLI prints the exact command that recreates the project (`tui/summary.ts`).
