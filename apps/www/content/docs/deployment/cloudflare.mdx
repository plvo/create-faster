## What create-faster adds

Cloudflare Workers is a project-level deployment platform. Generation is stack-aware per app: a Hono app gets a direct Workers config, a Next.js app gets an [OpenNext](https://opennext.js.org/cloudflare) config, and a TanStack Start app gets the [Cloudflare Vite plugin](https://developers.cloudflare.com/workers/vite-plugin/). Selecting it once with `--deployment cloudflare` configures every app according to its stack.

### Hono apps

Hono already exports a Workers-compatible fetch handler (`export default app`), so no adapter is needed — local dev keeps running on Bun while Wrangler handles preview and deploy.

```jsonc title="wrangler.jsonc"
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "my-api",
  "main": "src/index.ts",
  "compatibility_date": "2026-06-12",
  "compatibility_flags": ["nodejs_compat"]
}
```

**Scripts:**
- `deploy` - Deploy the Worker (`wrangler deploy`)
- `preview` - Run the Worker locally on the Workers runtime (`wrangler dev`)
- `cf-typegen` - Generate binding types (`wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`). The app's `postinstall` runs it, so a fresh install type-checks; run it again after each change to `wrangler.jsonc`.

### Next.js apps

Next.js apps deploy through the OpenNext Cloudflare adapter. `next.config.ts` calls `initOpenNextCloudflareForDev()` under `next dev` only (`NODE_ENV` is `development`), so Cloudflare bindings are available there and `next build` does not start a local workerd. The build emits the Worker output under `.open-next/`.

```jsonc title="wrangler.jsonc"
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "web",
  "main": ".open-next/worker.js",
  "compatibility_flags": ["nodejs_compat", "global_fetch_strictly_public"],
  "assets": {
    "directory": ".open-next/assets",
    "binding": "ASSETS"
  }
}
```

```typescript title="open-next.config.ts"
import { defineCloudflareConfig } from '@opennextjs/cloudflare';

export default defineCloudflareConfig({});
```

**Scripts:**
- `build:cf` - Generate binding types, then the OpenNext adapter build (`wrangler types … && opennextjs-cloudflare build`). `opennextjs-cloudflare build` runs the project's `build` script (`next build`) itself, in standalone mode, so `next build` is not repeated in `build:cf`. Types are generated first so the binding globals (e.g. `Hyperdrive`, `D1Database`) typecheck during that build.
- `preview` - Local Wrangler preview of the built output (`opennextjs-cloudflare preview`)
- `deploy` - Deploy the built output (`opennextjs-cloudflare deploy`)
- `cf-typegen` - Generate binding types (`wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`). The app's `postinstall` runs it, so a fresh install type-checks; run it again after each change to `wrangler.jsonc`.

A Next.js app on Workers has no `start` script: `next start` runs Next's Node server, where `getCloudflareContext()` is never initialised, so every page returns a 500. Run `build:cf` then `preview` to serve the production build in workerd.

### TanStack Start apps

TanStack Start runs on Workers through `@cloudflare/vite-plugin`, without Nitro: `vite.config.ts` registers the plugin in place of `nitro()`, and `vite dev` and `vite preview` run the app in workerd with the bindings declared in `wrangler.jsonc`. The Nitro `start` script and the `.env.start` file are not generated. The Vite config passes `vars: { NODE_ENV }` to the plugin, so the built `wrangler.json` sets `NODE_ENV=production` in `vite preview` and `wrangler deploy` while `vite dev` runs with `development`.

```jsonc title="wrangler.jsonc"
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "web",
  "main": "src/server.ts",
  "compatibility_date": "2026-06-12",
  "compatibility_flags": ["nodejs_compat"]
}
```

`src/server.ts` is the Worker entry: it exports Start's handler (`@tanstack/react-start/server-entry`). Libraries wrap it, for example the [evlog](/docs/modules/observability/evlog) module wraps `fetch` with `withEvlog`.

**Scripts:**
- `build` - Build the client assets and the Worker (`vite build`)
- `preview` - Serve the production build in workerd (`vite preview`). Check the build here before deploying: `vite dev` hides errors that only appear once the Worker is built, such as I/O or randomness at module level.
- `deploy` - Build then deploy (`vite build && wrangler deploy`)
- `cf-typegen` - Generate binding types (`wrangler types --env-interface CloudflareEnv cloudflare-env.d.ts`). The app's `postinstall` runs it, so a fresh install type-checks; run it again after each change to `wrangler.jsonc`: `tsc` reads `cloudflare-env.d.ts` for the `cloudflare:workers` module.

Bindings are read with `import { env } from 'cloudflare:workers'`. With `--database d1`, `src/lib/server.ts` builds the Drizzle `db` once at module scope from `env.DB`, which is safe for D1. With Postgres or MySQL, build a client per request with `await createDb(env.HYPERDRIVE)` (see below).

## Postgres / MySQL via Hyperdrive

A Worker cannot open a raw TCP connection to a Postgres or MySQL server, and forbids reusing a connection across requests. When a Next.js or TanStack Start app uses `--database postgres` (or `mysql`) with `--deployment cloudflare`, the database is routed through a Cloudflare [Hyperdrive](https://developers.cloudflare.com/hyperdrive/) binding (a pooling proxy), and the `db` package exports a per-request `createDb(hyperdrive)` factory instead of a module-level singleton.

```jsonc title="wrangler.jsonc"
"hyperdrive": [
  {
    "binding": "HYPERDRIVE",
    "id": "REPLACE_WITH_HYPERDRIVE_ID",
    "localConnectionString": "postgresql://postgres:password@localhost:5432/postgres-my-app"
  }
]
```

- **Setup:** `wrangler hyperdrive create <name> --connection-string="..."`, then paste the id into `wrangler.jsonc`. `localConnectionString` is used by local runs only (`wrangler dev`, `vite dev`, `vite preview`) and matches your local `DATABASE_URL`.
- **Migrations** run on Node via `drizzle-kit` or the `prisma` CLI against `DATABASE_URL` — unchanged by Hyperdrive.
- better-auth / tRPC over a Cloudflare binding database (per-request consumers) is not wired yet, so those combinations are disabled with a reason on Cloudflare (tracked in [#153](https://github.com/plvo/create-faster/issues/153)).

## Shared behavior

The Worker `name` is the project name in single mode and `<project>-<app>` in turborepo mode, so two projects deployed to one Cloudflare account never share a Worker.

**Modified files:**
- `.gitignore` - Ignores `.wrangler/` and `cloudflare-env.d.ts`; for Next.js apps it also ignores `.open-next/` and `.prod.env`.

## Runtime secrets

A variable that META marks as a server-side secret (`secret: true` on its `envs` entry: `BETTER_AUTH_SECRET` for [Better Auth](/docs/modules/auth/better-auth), for example) is listed in the `wrangler.jsonc` of every Worker app that receives it, under Wrangler's `secrets.required`:

```jsonc title="wrangler.jsonc"
"secrets": {
  "required": ["BETTER_AUTH_SECRET"]
}
```

An app without such a variable gets no `secrets` field. In a turborepo each Worker lists only its own: a Next.js app with Better Auth and a Hono app without it get different files. Public values (`NEXT_PUBLIC_*`, `VITE_*`) are never secrets.

With the field present:

- `wrangler deploy` fails until each secret is set. `wrangler secret put <KEY>` sets one on an existing Worker. A new Worker does not exist yet, so its first deploy takes them from a gitignored file (`wrangler deploy --secrets-file <file>`, with a file you keep out of git; for Next.js the `deploy` script takes `-- --secrets-file .prod.env`, a file the generated `.gitignore` lists).
- Local runs (`wrangler dev`, `vite preview`) warn about a missing one.
- `wrangler types` types each one as `string` in `cloudflare-env.d.ts`, whether or not a `.env` exists.

Local secrets go in `.env` (already gitignored), not `.dev.vars`: Wrangler ignores `.env` whenever a `.dev.vars` file is present, which would silently shadow it.

### Next.js: `.env` is bundled into the Worker

`build:cf` bundles every `.env*` value, server secrets included, into the Worker (`.open-next/cloudflare/next-env.mjs`) as a `process.env` fallback, and OpenNext has no opt-out. A secret set with `wrangler secret put` wins at runtime, but the bundled value is used silently when the secret was never set. So:

- Build the Worker you deploy where `.env` holds no real secret: in CI, or from a checkout without a `.env`.
- Set production secrets with `wrangler secret put`, or `--secrets-file` on the first deploy.
- `preview` serves the build as it is: the `.env` values are frozen when `build:cf` runs, so run it again after each `.env` change.
- Wrangler does not load `.env` for this preview (OpenNext handles it), so `preview` warns about a missing required secret even when `.env` holds it. The warning is safe to ignore then.

### TanStack Start: `dist/server/.dev.vars`

`vite build` writes `dist/server/.dev.vars`, a local copy of `.env` for `vite preview` (only the `secrets.required` keys when the Worker lists any). `wrangler deploy` does not upload it. Never ship `dist` other than through `wrangler deploy`, and rebuild after editing `.env`.

**Turborepo mode:**
`wrangler.jsonc` (and `open-next.config.ts` for Next.js apps) is placed in `apps/<name>/`, and the Worker is named `<project>-<app>`. Run the scripts from the app directory.
