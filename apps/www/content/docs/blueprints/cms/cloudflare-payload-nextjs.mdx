## Presentation

A content-managed website that runs entirely on Cloudflare Workers. Editors publish pages and posts from the [Payload](https://payloadcms.com) admin at `/admin`, and the public site serves them from the edge as soon as they are published, without a deploy. The database is [D1](/docs/database/d1), the media are in R2, and a scheduled [Hono](/docs/stacks/hono) Worker backs everything up every day.

It starts from the shape of Payload's own Cloudflare template (`with-cloudflare-d1`, Payload 3.x), which ships the admin and a welcome page, and adds what a site needs on top of it: public pages built from Payload content, a page cache that a publish expires, draft and live preview, a first admin created before the Worker is public, image handling without `sharp`, fixes for the D1 adapter, a migration workflow, and a backup Worker. Its bindings also stay local during a build: the official template asks for remote bindings when `NODE_ENV` is `production`, which `next build` sets. [Cloudflare Fullstack](/docs/blueprints/business/cloudflare-fullstack-nextjs) is an application dashboard and [Cloudflare Static Site](/docs/blueprints/business/cloudflare-static-site-nextjs) has no back office; this one is the blueprint with an editor in the loop.

## Composition

**Apps:**
- `web` - Next.js ([→ docs](/docs/stacks/nextjs)) through OpenNext + shadcn/ui ([→ module](/docs/modules/ui/shadcn)). It serves the Payload admin (`/admin`), the REST API (`/api`) and the public site.
- `cron` - Hono ([→ docs](/docs/stacks/hono)) scheduled Worker, the backups.

**Shared packages:** `packages/ui` (shadcn) and `packages/config` (TypeScript config).

**Project addons:**
- Database: [→ Cloudflare D1](/docs/database/d1), **without an ORM**. Payload owns the schema and its migrations, so there is no `packages/db`, no Drizzle file and no `db:generate` script.
- Deployment: [→ Cloudflare](/docs/deployment/cloudflare)

Payload 3.x supports Next.js only, which is why there is no TanStack Start variant. `payload` and every `@payloadcms/*` package are pinned to one exact version, declared once in META (`PAYLOAD_VERSION`): Payload publishes them together and each adapter checks the version of the core.

## Architecture

Blueprint-specific files only. The root `layout.tsx`, `not-found.tsx`, `error.tsx` and `page.tsx` of the Next.js stack are not generated: the admin group and the site group each render their own `<html>`.

## What's included

### Content model

- **Pages** are built from blocks: hero, rich text, media and call to action. The page with the slug `home` is the home page, served at `/` (and not at `/home`).
- **Posts** have a cover image, an excerpt, rich text (Lexical) and a publication date. They are listed at `/posts`, newest first.
- **Media** require an `alt`. They are images only, up to 20 MB.
- **Site settings** (a global) hold the site name, the header links (8 at most) and the footer text.
- **Users** are editors with access to the whole admin. The last user cannot be deleted, because an empty users collection lets the next visitor create the first one.
- Pages and posts have SEO fields (the field exports of `@payloadcms/plugin-seo`, not the plugin, whose generate endpoints no field uses), drafts with autosave, and at most 50 versions per document. Anyone reads a published document; a signed-in user also reads drafts.

The public site also serves `sitemap.xml` (published pages and posts) and `robots.txt`. `robots.txt` disallows everything on `localhost` and on a `workers.dev` address, so the site is not indexed until it is served from a custom domain set as `NEXT_PUBLIC_APP_URL`; on the production origin it allows the site and disallows `/admin/` and `/api/`.

### Cache and revalidation

Every read of the public site goes through `unstable_cache` with tags (`pages`, `posts`, `site-settings`, `media`, `page:<slug>`, `post:<slug>`). OpenNext keeps the rendered pages in R2, under an `incremental-cache/` prefix of the media bucket, and the tags in the `revalidations` table of D1, which one of the committed migrations creates. A page view therefore reads R2 and the tag cache, not D1.

The `afterChange` and `afterDelete` hooks of pages, posts and media, and of the site settings, expire the tags of the document (the previous slug too after a rename) and of its lists. A published, changed or deleted document reaches the site at once, and a new one exists without a deploy. A draft saved over a published document expires nothing.

- Slug routes export `generateStaticParams` returning `[]` and `revalidate = false`: a page is rendered on its first request and kept until a hook expires it.
- `/posts` and `sitemap.xml` are `force-dynamic` (their data still comes from the tagged cache). Built ahead, they would query D1 during `next build`, before the first migration, and the first deploy would fail with `no such table`.
- A slug with no document answers 404 and leaves nothing in the cache, so invented URLs do not fill R2.

### Drafts, preview and live preview

The admin's preview button and live preview open `/next/preview`, which checks `PREVIEW_SECRET` (in constant time), the signed-in Payload user and the path, then turns draft mode on. A draft is read for the signed-in user only: the draft cookie alone shows the published document. `RefreshRouteOnSave` refreshes the page as the editor types. The admin answers with `frame-ancestors 'self'`, so no other site can frame it.

### First admin

Payload lets the first visitor create a user while the users collection is empty, and a deployed Worker has a public address. `ensure-admin` creates the admin from `ADMIN_EMAIL` and `ADMIN_PASSWORD` when there is no user and does nothing otherwise. `ensure-admin:remote` does the same in the production database, before the first deploy; it requires a password of at least 12 characters. The credentials live in `.env.admin`, a file of its own, because OpenNext bundles every `.env*` file of the app into the Worker and a password has no place there.

### Migrations

The adapter runs with `push: false`: the schema only changes through committed migrations, in development too, so the local and the production database never diverge. The blueprint ships the initial migration, the `revalidations` table of the tag cache and an index on `posts.publishedAt`, with their `.json` snapshots (without snapshots, `migrate:create` writes the whole schema again instead of a delta).

1. Change a collection.
2. `migrate:create <name>` writes the migration and its snapshot into `apps/web/src/migrations/`. Read the SQL: it must be a delta. Commit both.
3. `migrate` applies it to the local database.
4. `generate:types` and `generate:importmap` regenerate `payload-types.ts` and the admin import map. Commit them too.
5. `db:migrate:remote` applies it to the production database, before the deploy that needs it.

Payload migrations are TypeScript, so `wrangler d1 migrations apply` cannot run them. The generated files (`payload-types.ts`, `importMap.js`, `src/migrations/*`) are excluded from the linter and formatter you choose, so they stay byte-identical to what Payload writes.

### Bindings stay local until you ask

Nothing in the project reaches your Cloudflare account unless a command says it does. `dev`, `build`, `build:cf` and `preview` run on local D1 and R2 state under `.wrangler/v3` at the repository root (the directory the cron Worker uses too). No binding in the committed `wrangler.jsonc` is `"remote": true`, because `next build` loads `payload.config.ts` and would otherwise reach the account on every build. `db:migrate:remote` and `ensure-admin:remote` write a throwaway Wrangler config with `DB` and `STORAGE` marked remote, run one script and delete the config. They need a Wrangler login (or `CLOUDFLARE_API_TOKEN`).

### Media without `sharp`

`sharp` is a native module that does not run on workerd, so the project configures none. An image is stored and served as uploaded, through Payload from R2 (`/api/media/file/<filename>`, with a week-long `Cache-Control`).

- No image sizes, no format conversion, no EXIF removal. Width, height, size and MIME type are still recorded.
- Crop and focal point are off in the admin (the server would silently drop the value). `focalX` and `focalY` fields (percent) take their place and are applied as the `object-position` of the image.
- `images.unoptimized` is `true`: the OpenNext image optimizer fetches through `ASSETS`, which does not hold media served from R2, and answered 404 for every image.
- Uploads are limited to 20 MB, refused with a 413 before anything is stored. A `beforeChange` hook applies the same limit to Local API uploads, which skip the multipart parser.
- Resizing at delivery uses Cloudflare Images transformations (`/cdn-cgi/image/`), which needs a zone: it answers 404 on `workers.dev`.

### D1 behaviors it works around or documents

- **Admin preferences.** `@payloadcms/db-d1-sqlite` never saves them (it sets `upsert` to `updateOne` without `upsert: true`). The `onInit` hook of `payload.config.ts` rebinds it ([payload#17202](https://github.com/payloadcms/payload/issues/17202)).
- **No transactions.** The adapter's transactions do nothing, so a failed hook does not roll a write back, and an array is replaced by deleting its rows and inserting them again. Array fields stay small: the blocks hold flat fields and the navigation stops at 8 links.
- **100 bound parameters per query.** A bulk update or publish of about a hundred documents fails.
- A bulk delete can answer 500 and still delete everything. A migration can print errors and end with `Done`: check the schema afterwards.
- GraphQL is disabled and its routes are not generated, because it is not guaranteed to run on workerd. The site reads through the Local API. The `graphql` package stays, as `@payloadcms/next` peers on it.
- The project builds with `next build --webpack`: Turbopack fails on Payload's server bundle. `next.config.ts` also sets one build worker (`experimental.cpus: 1`, `staticGenerationMaxConcurrency: 1`), because parallel workers drop the connection to the platform proxy.

### Cron Worker and backups

`apps/cron` runs daily at 03:00 UTC. It dumps every table of the D1 database (except `_cf_*`, which D1 refuses to read, and `sqlite_*`) as NDJSON, one object per table or more for a large one, plus a `manifest.json`, under `backups/<date>/<time>/` in a bucket of its own (`<project>-backups`, bound by the cron Worker only, so the Worker that serves the public media cannot read it). Backups older than `BACKUP_RETENTION_DAYS` (30, a var of `wrangler.jsonc`) are deleted by the next run.

The media files are not copied: they are already in the media bucket, and the `media` table of the dump is their index. D1 Time Travel rewinds the whole database to any point of the last 30 days and covers nothing of R2.

`POST /backup/run` runs a backup on demand. It needs `Authorization: Bearer <BACKUP_TRIGGER_TOKEN>`, compares the token in constant time and fails closed (503) when the token is not set. The generated README explains how to restore a table from a backup or with Time Travel.

### Seed

`db:seed` adds sample site settings, one image, the pages `home` and `about` and two posts. It adds only what is missing and deletes nothing: what you changed in the admin stays, and running it again changes nothing.

## Local setup

```bash
bun install
cp apps/web/.env.example apps/web/.env
cp apps/web/.env.admin.example apps/web/.env.admin
cp apps/cron/.env.example apps/cron/.env
# set PAYLOAD_SECRET and PREVIEW_SECRET in apps/web/.env, BACKUP_TRIGGER_TOKEN in apps/cron/.env
# (openssl rand -base64 32)
bun run migrate        # create the tables in the local D1
bun run ensure-admin   # create the admin of apps/web/.env.admin
bun run db:seed        # sample content
bun run dev
```

`dev` runs `next dev` for `web` on port 3000 and the cron Worker under `wrangler dev` on port 3001. Sign in at `http://localhost:3000/admin` with the email and password of `apps/web/.env.admin` (`admin@example.com` and `password` in the example).

| `migrate` | Apply the Payload migrations to the local database |

| `generate:types` | Regenerate the Cloudflare binding types and `payload-types.ts` |
| `generate:importmap` | Regenerate the import map of the admin |
| `ensure-admin` | Create the first admin of the local database when it has no user |

| `payload` (app) | The Payload CLI |

## Deploying

The Workers Paid plan is needed in practice: the Free plan allows 10 ms of CPU per request and 50 D1 queries per invocation, which an admin request exceeds. The order matters, and the generated README and `docs/agents/cloudflare-deploy.md` give every command for your package manager:

1. Create the D1 database and paste its `database_id` into both `wrangler.jsonc` files (they bind the same database).
2. Create the R2 media bucket (`<project>-storage`) and the backups bucket (`<project>-backups`). An account that never used R2 refuses with error `10042` until R2 is enabled in the dashboard.
3. Migrate the local database again: local data is keyed by the `database_id`, so the real id starts an empty one.
4. `db:migrate:remote`, then `ensure-admin:remote`, before the Worker is reachable.
5. Learn the production `workers.dev` URL (the Workers API gives the account subdomain), export it as `NEXT_PUBLIC_APP_URL` for the build, then `build:cf` and `deploy` the `web` Worker with its secrets, and deploy `cron`.
6. Check the site with a retry loop: routes answer 404 for about a minute after `wrangler deploy`.

Each Worker lists its runtime secrets under `secrets.required` (`PAYLOAD_SECRET` and `PREVIEW_SECRET` for `web`, `BACKUP_TRIGGER_TOKEN` for `cron`), so a deploy fails until they are set. `build:cf` bundles every `.env*` value of the app into the Worker, so build the one you deploy where `.env` holds no real secret. See [Cloudflare](/docs/deployment/cloudflare) for the deployment details.

## Environment variables

| Variable | Description |
|----------|-------------|
| `PAYLOAD_SECRET` | Payload's secret (scope: app `web`, secret). Generate with `openssl rand -base64 32` |
| `PREVIEW_SECRET` | Secret of the draft preview address (scope: app `web`, secret). Generate it the same way |
| `NEXT_PUBLIC_APP_URL` | Public URL of the site. Read by the preview links, live preview, sitemap and robots, and frozen into the build (scope: app `web`) |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | The first admin, read by `ensure-admin` only. In `apps/web/.env.admin`, a file of its own so OpenNext does not bundle them (scope: app `web`). The remote run needs a password of at least 12 characters |
| `BACKUP_TRIGGER_TOKEN` | Bearer token of `POST /backup/run` (scope: app `cron`, secret). Generate it the same way |

There is no database connection string: D1 is the `DB` binding only.
