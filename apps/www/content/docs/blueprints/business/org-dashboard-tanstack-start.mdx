## Presentation

The [Org Dashboard (Next.js)](/docs/blueprints/business/org-dashboard-nextjs) starter with a TanStack Start web app instead of Next.js. You get the same product: email/password login, roles an administrator edits at runtime (admin, user and manager to start with) enforced on the server and in the UI, an admin panel, a contacts CRUD, a profile area, a Node batch worker, a one-command local setup, and an idempotent seed. Only the web app changes: routing, route guards, and the production server follow TanStack Start.

## Composition

**Apps:**
- `web` — TanStack Start ([→ docs](/docs/stacks/tanstack-start)) + shadcn/ui ([→ module](/docs/modules/ui/shadcn)), Better Auth ([→ module](/docs/modules/auth/better-auth)), tRPC ([→ module](/docs/modules/api/trpc)), TanStack Query ([→ module](/docs/modules/data-fetching/tanstack-query)), TanStack Devtools ([→ module](/docs/modules/data-fetching/tanstack-devtools)), TanStack Form ([→ module](/docs/modules/forms/tanstack-form)), Next Themes ([→ module](/docs/modules/ui/next-themes))

## Shared with the Next.js variant

The blueprint inherits the templates of [Org Dashboard (Next.js)](/docs/blueprints/business/org-dashboard-nextjs) (META `extends`) and replaces only what is specific to the web framework. Everything else is the same, and documented on that page:

- the `api`, `auth`, `db`, `ui` and `config` packages, the tRPC routers (`user`, `contact`, `roles`, `permissions`, `session`) and the RBAC middleware (`adminProcedure`, `permissionProcedure`)
- the permission vocabulary in `packages/auth/src/permissions.ts`, the roles and their permissions in the database (`admin` compiled, `user` and `manager` written by `db:roles`), the role guard and the rules to create, edit, assign and delete roles
- the database schema, the Docker PostgreSQL setup, `scripts/local-setup.ts` and the seed (`--fixtures`, `--reset`, `--force`), with the same three accounts (`admin@example.com`, `user@example.com`, `manager@example.com`)
- the `batch` Node worker
- the pages: login, dashboard home, contacts list and detail, admin users list and detail, admin roles, and the four profile tabs (account, security, sessions, preferences)
- the generated `AGENTS.md` and `docs/agents/` guides (the TanStack Start variant documents its own guards in `docs/agents/auth.md`)

The contacts and admin pages render the same markup in both variants (shared partials), so the two apps look and behave alike.

## What differs from the Next.js variant

| | Next.js | TanStack Start |
|---|---|---|
| Routing | App Router, route groups `(auth)` and `(dashboard)` | File routes in `src/routes/`, pathless layouts `_auth` and `_dashboard` |
| Auth guard | `requireSession()` in the layout and in each protected page | `beforeLoad` of the `_dashboard` layout, once for every dashboard route |
| Admin and permission checks | `requireAdmin()` / `requirePermission()` in each page | `beforeLoad` of the `admin` and `contacts` layout routes, once for their pages, and of the dashboard home route, over the permission list the `_dashboard` route context holds |
| Permission list | `permissions.mine` prefetched by the dashboard layout inside `HydrateClient`, read from the query cache | `getPermissions` server function called by `beforeLoad` of `_dashboard`, serialized with the route context into the document, so hydrating the first page asks the server for nothing; `beforeLoad` runs again on each navigation, so a revocation reaches the next page the user opens |
| Data prefetch | Server component prefetch inside a `HydrateClient` boundary; a detail page awaits its record and calls `notFound()` for an unknown id | Route `loader` prefetch without awaiting, `useSuspenseQuery` in the component; a detail loader awaits its record and throws `notFound()` for an unknown id, with a `pendingComponent` skeleton meanwhile |
| List pages | `page` and `pageSize` read from the server component's `searchParams` and prefetched | `page` and `pageSize` search parameters validated in the route's `validateSearch`, read by the loader through `loaderDeps` |
| Command palette | Opens a result with `useRouter` of `next/navigation` | Opens a result with `useRouter` of TanStack Router, and reads the permission list from the `_dashboard` route context |
| Post-login redirect | Query parameter validated by `safeRedirectPath` | `redirectTo` search parameter validated in `validateSearch` with the same `safeRedirectPath` |
| Production server | `next start` | Nitro server (`.output/server/index.mjs`) started with Node |
| Profile tabs | Directional slide animation with React `ViewTransition` | Plain tab navigation, no transition |
| Email change notice | `searchParams` of the account page, `router.replace` drops the query | `validateSearch` of the account route, `navigate` drops the query |
| Background link delivery | `after` of `next/server` | `waitUntil` of the Nitro request; on a Lambda (`sst`, `terraform-aws`) there is none, so the auth route (`handleAuthRequest`) holds its answer until the delivery is done (two seconds at most), and an email change to a free address then answers later than one to a taken address (nothing is sent for it) by the time the mailer takes |

### Pathless layouts and guards

`_dashboard.tsx` and `_auth.tsx` add no segment to the URL. Both decide through one `isSignedIn(session)` check in `src/lib/auth/guards.ts`, so a session one layout accepts is never refused by the other and the two never redirect to each other in a loop:

- `_dashboard` calls `requireSession(location)` in `beforeLoad`. Without a session (or without a role) it redirects to `/login?redirectTo=<requested path>`, and returns `{ session, permissions }` into the route context (the permission list of the role, read from the database once per request), so every child route and component reads the session and the list from there. `beforeLoad` hooks run parent first and every loader starts after them, so an anonymous visit redirects before any protected query starts.
- `_auth` wraps the login page and redirects a signed-in user to `/`.
- `admin.tsx` calls `requireAdmin(context.session)` once for every page under `/admin`: a member is redirected to `/`. The bare `/admin` answers 404 through `admin/index.tsx`.
- `contacts.tsx` calls `requirePermission(context.permissions, { contact: ['read'] })` once for every page under `/contacts`: a role without the permission gets the not-found page with a 404 status. The dashboard home (`_dashboard/index.tsx`) makes the same `contact:read` check in its own `beforeLoad`.

The server still enforces every permission: each tRPC procedure keeps its `adminProcedure` or `permissionProcedure`, so the route guards only decide what a page shows.

### Validated redirect

The login route reads `redirectTo` in `validateSearch` and passes it through `safeRedirectPath` (`src/lib/safe-redirect.ts`): only an internal path survives, anything else falls back to `/`. The login form navigates to the validated destination and never to a raw query parameter.

### Session on the server

`getSession` (`src/lib/auth/session.ts`) is a server function that returns the current session through a per-request cache shared with the tRPC context, so a request looks the session up once. Better Auth uses the `tanstackStartCookies()` plugin, built into the app's own instance in `src/lib/auth/auth.ts`.

## What's included

The features (login, role-based access control, admin panel, contacts CRUD, profile, local setup and seed) are those of the [Next.js variant](/docs/blueprints/business/org-dashboard-nextjs#whats-included); [What differs](#what-differs-from-the-nextjs-variant) covers how the web app implements them. What is specific to this variant:

### Production server

`vite build` emits a Nitro server to `apps/web/.output/`. `start` runs it with Node, loading `.env` when it exists, then `.env.start` (`NODE_ENV=production` and the default `PORT`). In the turborepo, `bun run start` runs `turbo start`. A client-address Nitro plugin (`src/lib/nitro/client-ip.ts`) fills `x-forwarded-for` with the connection address when a request has none, so Better Auth rate limits each client separately when the server is exposed directly.

### Deployment

The blueprint supports the [SST](/docs/deployment/sst) deployment: `sst.config.ts` deploys the web app with `sst.aws.TanStackStart` on an AWS Lambda Nitro preset, and each runtime secret (`DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`) becomes an `sst.Secret`.

The Cloudflare deployments are not available, and the CLI rejects them with this blueprint:

- `--deployment cloudflare`: Better Auth uses a module-singleton database, while Cloudflare reaches PostgreSQL through a per-request binding (not yet supported).
- `--deployment cloudflare-static`: Better Auth needs a server runtime, which a static deployment does not provide.

The Next.js variant is rejected the same way.
